# CoreBank v0.3 — Transfers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Adicionar transferências internas atômicas entre contas CoreBank, com histórico correlacionado, concorrência segura e compatibilidade integral com depósitos e saques da v0.2.

**Architecture:** A v0.3 evolui o monólito modular existente. Um novo `TransferService` coordena duas contas e dois lançamentos `AccountTransaction` dentro de uma única transação Spring `@Transactional`, reutilizando `Account.deposit`, `Account.withdraw`, `AccountRepository`, `AccountTransactionRepository` e optimistic locking via `@Version`. A API entra por `POST /api/v1/transfers`, sem tabela dedicada `transfers`.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, PostgreSQL, Flyway, Bean Validation, JUnit 5, Mockito, MockMvc, Testcontainers, JaCoCo, Maven.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.3-transfers-design.md`

## Global Constraints

- Apenas transferências internas entre duas contas CoreBank.
- Origem e destino devem ser diferentes, existentes, `ACTIVE` e em `BRL`.
- Valor > 0 e com no máximo 2 casas decimais; sem arredondamento silencioso.
- Débito, crédito e os dois lançamentos devem ocorrer na mesma transação ACID.
- Cada transferência gera exatamente um `TRANSFER_OUT` e um `TRANSFER_IN` com o mesmo `transferId`.
- `counterpartyAccountId` deve apontar para a conta oposta; depósitos e saques permanecem com ambos os campos nulos.
- Concorrência continua protegida por optimistic locking com `@Version`; conflito retorna HTTP 409.
- Sem tabela `transfers`, PIX, conta externa, idempotency key, Kafka ou double-entry ledger nesta versão.
- Toda regressão da v0.2 deve ser detectada por `mvn clean verify`.

## Review Focus

- Transferência para a própria conta deve falhar antes de qualquer mutação de saldo.
- Falha ao gravar o segundo lançamento não pode deixar débito, crédito ou primeiro lançamento confirmados.
- Concorrência envolvendo a mesma origem ou o mesmo destino não pode gerar saldo perdido ou gasto duplicado.
- `transferId` e `counterpartyAccountId` devem ser obrigatórios apenas para `TRANSFER_OUT`/`TRANSFER_IN`, sem quebrar dados antigos.
- Descrição com espaços, vazia ou > 200 caracteres deve preservar exatamente a semântica já usada nas movimentações da v0.2.
