# CoreBank v0.7 — Retry + DLQ Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add durable retry scheduling and a transactionally safe dead-letter pipeline to the v0.6 Kafka transactional outbox without coupling financial transactions to Kafka availability.

**Architecture:** PostgreSQL remains the source of truth for publication state. Primary outbox retries are persisted with `attempt_count`, `next_attempt_at`, and sanitized error metadata; exhausted or non-retriable events atomically transition to `DEAD_LETTERED` and create a separate durable `dead_letter_events` row, which is then published asynchronously to `corebank.financial-events.dlq.v1` with its own indefinite durable backoff.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, PostgreSQL 17, Flyway, Spring Kafka, Testcontainers 1.21.3, JUnit 5, Mockito, JaCoCo, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.7-retry-dlq-design.md`

## Global Constraints

- Maximum primary publication attempts: `5`.
- Primary retry delays: `2s, 5s, 15s, 30s`; the fifth failure dead-letters the event.
- Non-retriable failures dead-letter immediately.
- `outbox_events.status`: `PENDING`, `PUBLISHED`, `DEAD_LETTERED`.
- Primary retry state is durable in PostgreSQL; do not use in-memory retry state as the source of truth.
- Primary eligible-row query uses `status = 'PENDING'`, `next_attempt_at <= NOW()`, ordering by `next_attempt_at, created_at`, and `FOR UPDATE SKIP LOCKED`.
- Dead-letter handoff is atomic in PostgreSQL: primary row becomes `DEAD_LETTERED` and exactly one `dead_letter_events` row is created in the same transaction.
- DLQ topic: `corebank.financial-events.dlq.v1`.
- DLQ retry delays: `5s, 15s, 30s, 60s`, then capped at `60s` indefinitely.
- No DLQ-of-DLQ and no redrive/admin endpoint in v0.7.
- Persist no full stack traces, request bodies, transaction descriptions, credentials, idempotency keys, balances, or customer PII in retry/DLQ error fields or payloads.
- Successful primary publication after retries preserves `attempt_count` and clears `last_error_type` / `last_error_message`.
- `dead_letter_events` keeps original failure metadata separate from DLQ-publication failure metadata via `last_publish_error_type` / `last_publish_error_message`.
- Maintain at-least-once semantics; do not claim exactly-once delivery.
- Do not add Redis, JWT/RBAC, frontend, consumer idempotency, or service extraction in this release.
- Keep PR workflow; do not merge to `main` without explicit user approval.

## Review Focus

- A legacy v0.6 `PENDING` row migrated to v0.7 must be immediately eligible and start at `attempt_count = 0`; pin this in migration integration tests.
- A primary event that fails once and later succeeds must keep `attempt_count = 1` while clearing active error fields; pin this in worker integration tests.
- A deterministic serialization failure must bypass the remaining retry budget and produce exactly one dead-letter row; pin this in classification/dead-letter integration tests.
- Concurrent workers must not publish or dead-letter the same primary or DLQ row twice while the row is locked; pin this in concurrency integration tests.
- A DLQ Kafka outage lasting through many scheduler cycles must keep the record durable, increase `publish_attempts`, cap delay at 60 seconds, and never create a second dead-letter layer; pin this in DLQ publisher tests.
