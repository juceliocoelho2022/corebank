# CoreBank v0.4 — Double-entry Ledger Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an immutable double-entry ledger for deposits, withdrawals and internal transfers while keeping `accounts.balance` as the operational balance and adding account-level reconciliation.

**Architecture:** CoreBank remains a modular monolith. Existing `TransactionService` and `TransferService` keep ownership of business flows and call a new `LedgerService` inside the same Spring transaction; `ReconciliationService` compares operational balances with ledger positions. `ledger_accounts`, `journal_entries` and `ledger_entries` are append-only, with PostgreSQL triggers blocking updates/deletes.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, PostgreSQL 17, Flyway, Bean Validation, JUnit 5, Mockito, MockMvc, Testcontainers, JaCoCo, Maven.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.4-double-entry-ledger-design.md`

## Global Constraints

- Backend only; no frontend in v0.4.
- `accounts.balance` remains the operational balance; ledger is not the sole source of truth yet.
- Deposits, withdrawals and internal transfers must all create balanced journals.
- Every financial operation creates exactly one `journal_entry`; v0.4 business journals contain exactly two `ledger_entries`.
- `SUM(DEBIT) = SUM(CREDIT)` for every completed journal.
- Customer ledger accounts use type `CUSTOMER_LIABILITY` and code `CUSTOMER:<accountId>`.
- System clearing account uses type `CASH_CLEARING` and code `TECH:CASH_CLEARING`.
- BRL only.
- Operational state, transaction history, journal and ledger entries share one ACID boundary.
- Journal/ledger records are append-only in Java usage and PostgreSQL.
- Existing deposit, withdrawal and transfer HTTP contracts remain compatible.
- Reconciliation reports divergence but never auto-corrects it.
- `OPENING_BALANCE` is a technical journal type used only for migration/backfill; its `reference_id` is the CoreBank account id.
- No Kafka, idempotency, reversals API, pessimistic locking or microservices in v0.4.

## Review Focus

- Existing non-zero accounts after upgrade must reconcile immediately through `OPENING_BALANCE`, not appear as false mismatches.
- A ledger failure after an operational balance change must roll back balance, account history, journal and ledger rows together.
- Creating a new CoreBank account must also create exactly one `CUSTOMER_LIABILITY` in the same transaction.
- Append-only triggers must reject both `UPDATE` and `DELETE` without blocking normal inserts.
- Reconciliation must use liability semantics `credits - debits`, preserve 2-decimal money semantics, and return `404` for a missing CoreBank account.
