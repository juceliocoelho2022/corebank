# CoreBank v0.8 — Redis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Redis as a disposable, fail-open performance layer for safe Customer/Account summary reads and completed idempotency replay lookup without weakening any PostgreSQL-backed banking invariant.

**Architecture:** PostgreSQL remains the source of truth. Spring Cache serves two safe read models with five-minute TTLs; an explicit `StringRedisTemplate` adapter stores one-hour idempotency replay pointers keyed by SHA-256 of the raw `Idempotency-Key`. Redis never stores balances, full financial replay bodies, `IN_PROGRESS` state, locks, customer document/email, outbox state, or DLQ state. New replay pointers are written only after the PostgreSQL transaction commits.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, Spring Data Redis/Lettuce, PostgreSQL 17, Apache Kafka 3.8.1, Flyway, Testcontainers 1.21.3, JUnit 5, Mockito, MockMvc, JaCoCo, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.8-redis-design.md`

## Global Constraints

- Redis is an optimization only: **Redis OFF = CoreBank remains correct**.
- PostgreSQL remains authoritative for balances, ledger, idempotency, locking, outbox, and DLQ state.
- Do not cache `balance`, `balanceBefore`, `balanceAfter`, full `TransactionResponse`, full `TransferResponse`, Customer document/email, request payloads, or raw `Idempotency-Key` values.
- Customer and Account summary TTL: `5m` by default.
- Idempotency replay-pointer TTL: `1h` by default.
- Exact key namespaces:
  - `corebank:v1:customer-summary:{customerId}`
  - `corebank:v1:account-summary:{accountId}`
  - `corebank:v1:idempotency:{sha256(rawIdempotencyKey)}`
- Spring Cache is used only for safe Customer/Account summary projections.
- Idempotency replay uses an explicit Redis adapter; Redis never decides whether a financial command is safe to execute.
- Redis failures are fail-open. Cache `GET`, `PUT`, and `EVICT` failures must not fail a valid request whose PostgreSQL work is otherwise correct.
- A newly completed idempotency pointer must be written only **AFTER_COMMIT**.
- Existing complete Customer and Account endpoints remain PostgreSQL-authoritative.
- Deposits, withdrawals, and transfers do not invalidate `AccountSummary`, because balance is excluded from that projection.
- Redis is ephemeral in Docker Compose; do not add Redis persistence volumes.
- Redis being unavailable must not make global application health `DOWN` by itself.
- No Flyway migration is expected for v0.8 unless implementation discovers a separately justified PostgreSQL schema need.
- Do not add rate limiting, JWT/RBAC, frontend work, microservices, or broad observability scope in v0.8.
- Keep all implementation on `feature/corebank-v0.8`; never merge to `main` without explicit user approval.
- Use larger implementation checkpoints. Focused tests belong inside each task, but do not ask the user to manually run Maven after every tiny edit.

## Review Focus

- A Redis summary value must be an explicit safe DTO, never a JPA entity dump; Customer cache must exclude `document`/`email`, and Account cache must exclude `balance`, `version`, and `updatedAt`.
- A Redis replay hit is advisory only: the service must fetch the pointed PostgreSQL `IdempotencyRecord`, verify the raw-key record, operation, request hash, status, and pointer metadata, then replay the body from PostgreSQL.
- A stale, malformed, missing-record, mismatched, or non-`COMPLETED` pointer must be evicted best-effort and fall back to the existing PostgreSQL path; it must never cause command re-execution by itself.
- A successful financial commit followed by Redis write failure must still return according to the committed PostgreSQL outcome; a PostgreSQL rollback must leave no Redis pointer for the failed operation.
- Full Redis loss (`FLUSHALL`/container recreation) must rebuild summaries and replay pointers without duplicate financial effects or banking-data loss.

record.resourceId == pointer.resourceId
