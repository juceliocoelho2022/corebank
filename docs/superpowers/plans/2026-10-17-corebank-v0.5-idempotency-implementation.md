# CoreBank v0.5 — Idempotency Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add persistent, PostgreSQL-backed HTTP idempotency for deposits, withdrawals and internal transfers so retries never duplicate financial effects.

**Architecture:** Add a dedicated `com.corebank.idempotency` module that validates keys, computes canonical SHA-256 request fingerprints, reserves keys, persists original responses and replays completed results. The idempotency orchestration wraps the existing financial services inside the same Spring transaction; PostgreSQL remains the correctness authority through a unique key constraint, with `pg_try_advisory_xact_lock` used as a non-blocking cross-instance fast-fail for concurrent same-key requests.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, PostgreSQL 17, Flyway, Jackson, Bean Validation, JUnit 5, Mockito, MockMvc, Testcontainers, JaCoCo, Maven.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.5-idempotency-design.md`

## Global Constraints

- Backend only; no frontend in v0.5.
- `Idempotency-Key` is mandatory for deposit, withdrawal and transfer POST endpoints.
- Key length is 8–128 characters and values are opaque/case-sensitive.
- Keys are globally unique in v0.5.
- Supported operations are `DEPOSIT`, `WITHDRAWAL`, `TRANSFER`.
- Supported states are `IN_PROGRESS`, `COMPLETED`.
- Same key + same operation + same canonical request must replay the original body/status without new financial effects.
- Same key + different operation or request hash returns `409 Conflict`.
- Same key already executing must fail fast with `409 Conflict`; no JVM-local lock and no application polling.
- Idempotency reservation, financial mutation, transaction history, double-entry journal and completed replay data share one ACID boundary.
- Failed business/database operations must not leave a stale committed `IN_PROGRESS` record.
- No TTL, cleanup scheduler, Redis, Kafka, JWT/client scoping or customer/account-create idempotency in v0.5.
- Release target is `0.5.0`.

## Review Focus

- `100`, `100.0` and `100.00` must fingerprint identically after monetary normalization.
- `null`, blank and padded descriptions must fingerprint using the existing normalized business value, not raw JSON text.
- A concurrent same-key request must never create a second account transaction/journal even when requests reach different application instances.
- A failed command must roll back both its idempotency reservation and all partial financial writes.
- Replaying persisted JSON must preserve UUIDs, timestamps, decimals and the original HTTP status exactly enough for the existing response contracts.
