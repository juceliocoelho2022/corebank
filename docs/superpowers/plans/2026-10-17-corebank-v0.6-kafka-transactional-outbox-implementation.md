# CoreBank v0.6 Kafka Transactional Outbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add durable financial-event publication through Apache Kafka using a PostgreSQL Transactional Outbox without weakening CoreBank's existing financial, ledger, reconciliation, concurrency, or idempotency guarantees.

**Architecture:** Deposits, withdrawals, and internal transfers persist one `PENDING` outbox row in the same PostgreSQL transaction as balance/history/ledger/idempotency changes. A separate per-event publisher transaction claims one pending row with `FOR UPDATE SKIP LOCKED`, publishes the serialized envelope to Kafka, waits for broker acknowledgement, then marks the row `PUBLISHED`; failures roll back only the publisher transaction so the row remains `PENDING` for the next scheduler cycle.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, PostgreSQL 17, Flyway, Spring Kafka, Apache Kafka 3.8.1 KRaft, Jackson, Testcontainers 1.21.3, JUnit 5, Mockito, MockMvc, Maven, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.6-kafka-transactional-outbox-design.md`

## Global Constraints

- Target release is exactly `0.6.0`; base release is `0.5.0`.
- Keep CoreBank a modular monolith; do not extract services or add business Kafka consumers.
- Financial event types are exactly `DEPOSIT_COMPLETED`, `WITHDRAWAL_COMPLETED`, and `TRANSFER_COMPLETED`.
- Use one topic: `corebank.financial-events.v1`, 3 partitions, replication factor 1 for local development/tests.
- Delivery semantics are at-least-once; never claim exactly-once delivery.
- `outbox_events.id` is the same UUID exposed as `eventId` in the Kafka envelope.
- Event payloads must not include customer name/e-mail/document, authentication data, account balance, HTTP payload, `Idempotency-Key`, stack traces, infrastructure objects, or free-form transaction `description`.
- `DEPOSIT_COMPLETED` and `WITHDRAWAL_COMPLETED` use `accountId` as Kafka `message_key`; `TRANSFER_COMPLETED` uses `sourceAccountId`.
- Deposit/withdrawal `correlationId` is `AccountTransaction.id`; transfer `correlationId` is `transferId`.
- A successful real financial operation creates exactly one outbox row; an idempotent replay creates zero additional rows.
- Kafka availability must not participate in the HTTP financial transaction success path.
- No `FAILED` outbox status, retry counter, exponential backoff, max-attempt policy, DLQ, Redis, Schema Registry, Avro/Protobuf, Kafka transactions, JWT/RBAC, custom Prometheus metrics, or microservices in v0.6.
- Keep existing Testcontainers BOM `1.21.3` unless an actual compatibility failure proves a targeted change is required.
- Use `KafkaTemplate<String, String>` and explicit Jackson JSON serialization; do not publish JPA entities directly.
- Publisher concurrency correctness must come from PostgreSQL `FOR UPDATE SKIP LOCKED`, not JVM-local locks.
- Publisher completion is per event: Kafka ACK before marking `PUBLISHED`; send failure leaves the event `PENDING`.
- Preserve existing endpoints and v0.5 idempotency response/replay behavior.

## Review Focus

1. **Idempotent HTTP replay:** repeating the same successful deposit/transfer must keep outbox count at exactly one; pinned by Task 3 integration tests.
2. **Sensitive/free-form data leakage:** `description` and customer data must be absent from serialized payload/envelope; pinned by Task 2 factory tests and Task 7 Kafka payload assertions.
3. **Broker failure after financial commit:** a send failure must leave the already-committed financial operation intact and the outbox row `PENDING`; pinned by Task 5 and Task 7 tests.
4. **Concurrent publishers:** overlapping workers must not publish the same locked row simultaneously; a second worker must skip it and claim another pending row or return empty; pinned by Task 6 concurrency test.
5. **Crash/DB failure after Kafka ACK:** the design permits re-delivery because publication is at-least-once; Task 5 tests ACK-before-`PUBLISHED` ordering and Task 8 documents the duplicate window explicitly.

**Interfaces:**
- Add repository method:
  `Optional<OutboxEvent> findNextPendingForUpdate()` backed by native PostgreSQL `WHERE status='PENDING' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1`.
- Produce `OutboxPublicationWorker#publishNext() -> boolean`.
- `publishNext()` runs with `@Transactional(propagation = Propagation.REQUIRES_NEW)`.
- Return `false` when no pending row is claimable; return `true` only after one row receives Kafka ACK and is marked `PUBLISHED`.
- Publish using `KafkaTemplate<String,String>.send(topic, event.getMessageKey(), json)` and wait for the returned future to complete before `markPublished(Instant.now())`.
- Serialize `event.toEnvelope()` through the application `ObjectMapper`.
- On send/serialization failure, throw so the publisher transaction rolls back and the row remains `PENDING`.
- If waiting is interrupted, restore the thread interrupt flag before propagating an application exception.
