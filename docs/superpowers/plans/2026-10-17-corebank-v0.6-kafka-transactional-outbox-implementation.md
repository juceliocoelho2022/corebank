# CoreBank v0.6 Kafka Transactional Outbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish durable financial events to Kafka through a PostgreSQL Transactional Outbox while preserving the v0.5 ACID/idempotency guarantees.

**Architecture:** Deposits, withdrawals and transfers persist one `PENDING` outbox row in the same PostgreSQL transaction as financial state, ledger and idempotency. A separate per-event publisher transaction claims one row with `FOR UPDATE SKIP LOCKED`, sends it through `KafkaTemplate<String,String>`, waits for ACK, then marks the row `PUBLISHED`; send failure rolls back only that publisher transaction so the row remains `PENDING` for a later scheduler cycle.

**Tech Stack:** Java 21, Spring Boot 3.5.6, Spring Data JPA, PostgreSQL 17, Flyway, Spring Kafka, Apache Kafka 3.8.1 KRaft, Jackson, Testcontainers 1.21.3, JUnit 5, Mockito, MockMvc, Maven, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-10-17-corebank-v0.6-kafka-transactional-outbox-design.md`

## Global Constraints

- Target release: `0.6.0`; base release: `0.5.0`.
- Keep CoreBank a modular monolith.
- Event types are exactly `DEPOSIT_COMPLETED`, `WITHDRAWAL_COMPLETED`, `TRANSFER_COMPLETED`.
- One Kafka topic: `corebank.financial-events.v1`; local/test defaults: 3 partitions, replication factor 1.
- Delivery is **at-least-once**; never claim exactly-once.
- `outbox_events.id` is the Kafka `eventId`.
- `eventVersion` starts at `1`.
- Deposit/withdrawal: `aggregateType=ACCOUNT`, `aggregateId=accountId`, `correlationId=AccountTransaction.id`, `message_key=accountId`.
- Transfer: `aggregateType=TRANSFER`, `aggregateId=transferId`, `correlationId=transferId`, `message_key=sourceAccountId`.
- Event payloads must exclude customer name/e-mail/document, auth data, account balances, HTTP payload, `Idempotency-Key`, stack traces, infrastructure objects and free-form `description`.
- One real financial operation creates one outbox event; idempotent replay creates zero additional events.
- Kafka availability must never participate in the HTTP financial transaction success path.
- No `FAILED` status, retry counter, backoff, max attempts, DLQ, Redis, business consumers, Schema Registry, Avro/Protobuf, Kafka transactions, JWT/RBAC, custom metrics or microservices in v0.6.
- Keep Testcontainers BOM `1.21.3` unless a real compatibility failure proves otherwise.
- Use `KafkaTemplate<String,String>` plus explicit Jackson serialization.
- Publisher coordination must use PostgreSQL `FOR UPDATE SKIP LOCKED`, not JVM locks.
- A row becomes `PUBLISHED` only after Kafka ACK.
- On Kafka failure, leave the row `PENDING` and stop the current batch; retry on the next scheduler cycle.
- Preserve all existing endpoints and v0.5 idempotency semantics.

## Review Focus

1. **Replay duplication:** same `Idempotency-Key` must not create another outbox row — Task 3.
2. **Sensitive/free-form leakage:** `description` and customer data must be absent from payloads — Tasks 2 and 7.
3. **Broker failure after financial commit:** HTTP/financial state remains successful while outbox stays `PENDING` — Tasks 5 and 7.
4. **Concurrent publishers:** a locked row must be skipped, not double-published — Task 6.
5. **ACK-before-DB-commit crash window:** re-delivery remains possible and documented as at-least-once — Tasks 5 and 8.

### Task 5: Publish one claimed event transactionally

**Files:** modify repository; create `OutboxPublicationWorker`; create `OutboxPublicationWorkerIT`.

**Interfaces:**
- `OutboxEventRepository#findNextPendingForUpdate() -> Optional<OutboxEvent>` using native PostgreSQL:
  `WHERE status='PENDING' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1`.
- `OutboxPublicationWorker#publishNext() -> boolean` with `@Transactional(propagation = REQUIRES_NEW)`.
- return `false` if nothing claimable;
- return `true` only after Kafka ACK and `markPublished(...)`;
- serialize `event.toEnvelope()` with application `ObjectMapper`;
- send via `KafkaTemplate<String,String>.send(topic, event.getMessageKey(), json)` and wait for its future;
- serialization/send/wait failure throws so DB transaction rolls back;
- on interruption restore interrupt flag before propagating.

- [ ] **Step 1 — Write failing worker integration tests**
Success: one pending row -> exact topic/key/envelope sent -> row `PUBLISHED` with timestamp.

Failure: failed Kafka future -> worker throws -> fresh DB read still `PENDING`, `publishedAt=null`.

ACK ordering: incomplete future holds worker; row must not be committed `PUBLISHED` until future completes successfully.

- [ ] **Step 3 — Implement claim/send/mark transaction**

### Task 6: Bounded scheduler and concurrent publishers

**Files:** `OutboxPublisher`, `OutboxScheduler`, `CoreBankApplication`, `OutboxPublisherTest`, `OutboxConcurrencyIT`.

**Interfaces:**
- `OutboxPublisher#publishPendingBatch() -> int`
- loop at most `OutboxProperties.batchSize()` times;
- `worker.publishNext()==false` => stop normally;
- worker throws => log and **stop the current batch immediately** so the same oldest failed row is not retried repeatedly in one cycle;
- return count of successful publications before stop;
- `OutboxScheduler#publishPending()` calls publisher;
- `@Scheduled(fixedDelayString="${corebank.outbox.fixed-delay-ms:2000}", initialDelayString="${corebank.outbox.fixed-delay-ms:2000}")`;
- add `@EnableScheduling` once in `CoreBankApplication`.
