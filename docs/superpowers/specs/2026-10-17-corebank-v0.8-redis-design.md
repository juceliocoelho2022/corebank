# CoreBank v0.8 — Redis Design

## Status

Approved architectural design, pending final user review of this written specification.

## Context

CoreBank v0.7 established durable retry and dead-letter handling while preserving PostgreSQL as the source of truth for financial state, idempotency state, outbox state, and DLQ state.

v0.8 introduces Redis strictly as a secondary performance layer. Redis must never become authoritative for balances, ledger state, durable idempotency, locking, outbox state, DLQ state, or any other financial invariant.

Architectural principle:

> Redis accelerates CoreBank; PostgreSQL guarantees CoreBank.

## Goals

v0.8 must:

1. add Redis as a non-authoritative cache layer;
2. introduce cache-aside summaries for Customer and Account reads;
3. keep balances out of Redis;
4. keep sensitive Customer PII out of Redis;
5. accelerate idempotency replay lookup without storing the full financial response in Redis;
6. keep PostgreSQL as the durable authority for idempotency and locking;
7. remain operational when Redis is unavailable;
8. use short, explicit Redis timeouts;
9. use deterministic, versioned Redis key names;
10. prove fail-open behavior and cache loss recovery with integration tests.

## Non-goals

Not part of v0.8:

- caching account balances;
- caching full Customer responses;
- caching full Account responses;
- moving idempotency locks to Redis;
- moving `IN_PROGRESS` idempotency state to Redis;
- storing complete financial response bodies in Redis;
- Redis-backed rate limiting;
- JWT/RBAC;
- distributed transactions between PostgreSQL and Redis;
- Redis as a durable database;
- Redis persistence/volume requirements;
- frontend work;
- microservice extraction;
- observability dashboards beyond basic sanitized logging.

## Core invariants

PostgreSQL remains the source of truth.

The following must remain correct with Redis completely unavailable or fully flushed:

- deposits;
- withdrawals;
- transfers;
- balances;
- ledger entries;
- idempotency guarantees;
- outbox publication state;
- DLQ state;
- complete Customer reads;
- complete Account reads.

Redis failure must never cause financial duplication, data loss, or invalidation of a PostgreSQL transaction that committed successfully.

No code path may require an atomic PostgreSQL + Redis commit.

## Redis responsibilities

Redis may store only the following categories in v0.8:

```text
CustomerSummary cache
AccountSummary cache
Completed idempotency replay pointer
```

Redis must not store, as authoritative or cached business state:

```text
balance
balanceBefore
balanceAfter
ledger state
outbox state
DLQ state
idempotency IN_PROGRESS state
idempotency lock state
full idempotency response body
customer document
customer email
financial request payloads
```

## Read-model architecture

Summary endpoints use cache-aside behavior:

```text
HTTP request
    ↓
Spring Cache
    ↓ HIT
return cached summary

MISS / Redis error
    ↓
PostgreSQL
    ↓
map to safe summary DTO
    ↓
best-effort Redis put
    ↓
return response
```

Redis unavailability is treated as cache degradation, not application failure.

## Customer API design

The existing full endpoint remains unchanged:

```text
GET /api/v1/customers/{id}
```

It continues to read from PostgreSQL and may return the current complete representation including document and email.

Introduce:

```text
GET /api/v1/customers/{id}/summary
```

`CustomerSummary` contains only:

```text
id
name
createdAt
```

It must not contain:

```text
document
email
```

The summary endpoint uses Redis cache-aside with a TTL of five minutes.

If the Customer does not exist, PostgreSQL remains responsible for the authoritative 404 decision. Null/not-found results are not cached.

## Account API design

The existing full endpoint remains unchanged:

```text
GET /api/v1/accounts/{id}
```

It continues to read from PostgreSQL because the complete representation includes `balance`.

Introduce:

```text
GET /api/v1/accounts/{id}/summary
```

`AccountSummary` contains only:

```text
id
customerId
branch
number
status
currency
createdAt
```

It must not contain:

```text
balance
version
updatedAt
```

The summary endpoint uses Redis cache-aside with a TTL of five minutes.

Deposits, withdrawals, and transfers do not require invalidation of `AccountSummary` because balance is intentionally excluded from the cached projection.

## Summary cache TTL

Both summary caches use:

```text
TTL = 5 minutes
```

The TTL is externally configurable and defaults to five minutes.

## Summary cache keys

Use deterministic, versioned key namespaces:

```text
corebank:v1:customer-summary:{customerId}
corebank:v1:account-summary:{accountId}
```

The cache namespace version allows future payload/key changes without collisions with prior Redis data.

Customer and Account UUIDs may appear in these cache keys because they are internal technical identifiers and not secrets.

## Summary serialization

Cache values use JSON serialization through Jackson and dedicated summary DTOs/projections.

Requirements:

- no Java native serialization;
- no JPA entity serialization;
- no polymorphic domain-object dump;
- only explicit summary fields are serialized;
- serialization format must be deterministic enough for tests and safe migration by key namespace versioning.

## Summary invalidation

Current v0.8 create flows do not require invalidation because newly created UUIDs have no pre-existing cache entry.

Future updates to fields represented in a summary must evict that summary key after the PostgreSQL transaction commits successfully.

Examples:

```text
Customer name update -> evict customer-summary after commit
Account status update -> evict account-summary after commit
```

Eviction must never occur before the authoritative PostgreSQL commit.

A Redis eviction failure must not fail the business transaction. TTL bounds stale-data lifetime.

## Idempotency replay cache

Redis accelerates lookup of already completed idempotent operations without replacing the durable PostgreSQL record.

Redis stores a replay pointer, not the full response.

Logical pointer payload:

```json
{
  "recordId": "uuid",
  "operation": "DEPOSIT",
  "requestHash": "lower-case-sha256",
  "resourceId": "uuid-or-null",
  "httpStatus": 201
}
```

The pointer represents only a PostgreSQL `IdempotencyRecord` whose durable status is `COMPLETED`.

Redis must never store an `IN_PROGRESS` pointer.

## Idempotency replay TTL

Replay pointers use:

```text
TTL = 1 hour
```

The TTL is externally configurable and defaults to one hour.

Expiry of the pointer never expires the durable idempotency record in PostgreSQL.

A Redis miss simply falls back to the existing PostgreSQL idempotency flow.

## Idempotency cache key

The original `Idempotency-Key` must never appear in a Redis key.

Compute:

```text
SHA-256(UTF-8 raw Idempotency-Key)
```

and encode as lower-case hexadecimal.

Redis key format:

```text
corebank:v1:idempotency:{sha256}
```

The original idempotency key must not be logged by the cache layer.

## Idempotency replay flow

For an incoming idempotent request:

1. compute the SHA-256 cache-key digest from the incoming `Idempotency-Key`;
2. attempt Redis lookup;
3. on Redis hit, validate cached `operation` and `requestHash` against the incoming request;
4. use `recordId` to fetch the authoritative PostgreSQL `IdempotencyRecord`;
5. require PostgreSQL status `COMPLETED`;
6. use the PostgreSQL response body and HTTP status as the returned replay;
7. if the Redis pointer is missing, stale, malformed, points to a missing row, or points to a non-`COMPLETED` row, ignore it and execute the existing PostgreSQL path;
8. conflict semantics remain defined by PostgreSQL and the existing idempotency rules.

Redis never decides that a financial command is safe to execute again.

## Idempotency cache population

For a newly completed idempotent command:

```text
PostgreSQL transaction
    ↓
IdempotencyRecord -> COMPLETED
    ↓
COMMIT
    ↓
AFTER_COMMIT
    ↓
best-effort Redis replay-pointer write
```

The pointer must not be created before the PostgreSQL commit.

Implementation may use `@TransactionalEventListener(phase = AFTER_COMMIT)` or an equivalent Spring transaction synchronization mechanism.

For an already durable `COMPLETED` record found in PostgreSQL after a Redis miss, the pointer may be repopulated immediately/best-effort because the record was committed previously.

## Idempotency pointer corruption/staleness

A Redis pointer is advisory.

If the pointer:

- cannot be deserialized;
- has an invalid/missing field;
- points to a missing PostgreSQL record;
- points to a non-`COMPLETED` record;
- disagrees with PostgreSQL;

then the implementation must:

1. ignore the pointer;
2. best-effort evict it;
3. fall back to PostgreSQL;
4. preserve existing idempotency correctness.

Redis data never overrides PostgreSQL state.

## Spring Cache usage

Use Spring Cache for the simple summary read models.

Recommended approach:

```text
CustomerSummaryService -> @Cacheable("customer-summary")
AccountSummaryService  -> @Cacheable("account-summary")
```

A Redis-backed `CacheManager` provides TTL, serialization, and key prefixing.

Business/domain services should not be littered with direct `RedisTemplate` calls.

## Explicit Redis access for idempotency

Idempotency replay is not a generic cache concern because it requires explicit validation of:

- operation;
- requestHash;
- recordId;
- durable status.

Use a dedicated abstraction such as:

```java
interface IdempotencyReplayCache {
    Optional<ReplayPointer> find(String idempotencyKey);
    void putCompleted(String idempotencyKey, ReplayPointer pointer);
    void evict(String idempotencyKey);
}
```

The Redis implementation owns hashing, JSON serialization, TTL, and fail-open Redis access.

A `StringRedisTemplate` plus explicit Jackson serialization is preferred for replay pointers because the stored schema is small, explicit, and versioned.

## Fail-open policy

Redis is optional for application correctness.

### Cache read failure

```text
Redis GET fails
-> treat as cache miss
-> query PostgreSQL
-> return authoritative result
```

### Cache write failure

```text
Redis PUT fails
-> log sanitized warning
-> return successful business response
```

### Cache eviction failure

```text
Redis EVICT fails
-> log sanitized warning
-> continue
-> TTL eventually removes stale cache
```

Only Redis access/serialization problems in the cache layer are swallowed. Business exceptions and PostgreSQL failures must retain their normal semantics.

## Redis error handling

For Spring Cache, define a custom `CacheErrorHandler` that treats Redis get/put/evict failures as non-fatal degradation.

For explicit idempotency Redis access, catch Redis/DataAccess-layer failures locally, log only sanitized operational metadata, and fall back to PostgreSQL.

Do not catch and suppress unrelated business exceptions.

## Redis connection configuration

Default local configuration:

```yaml
spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
      connect-timeout: 500ms
      timeout: 500ms

corebank:
  cache:
    key-prefix: "corebank:v1:"
    summary-ttl: 5m
    idempotency-replay-ttl: 1h
```

Exact Spring property spelling must be verified against Spring Boot 3.5.6 during implementation.

Timeouts are deliberately short because Redis is an optimization and must not stall financial requests for seconds when degraded.

## Redis dependency

Add Spring Data Redis through Spring Boot dependency management, preferably:

```text
spring-boot-starter-data-redis
```

Use the Spring Boot managed Lettuce client unless implementation evidence requires a different client.

No custom Redis client version should be pinned without a concrete reason.

## Docker Compose

Add a local Redis service:

```yaml
redis:
  image: redis:7-alpine
  container_name: corebank-redis
  ports:
    - "6379:6379"
  healthcheck:
    test: ["CMD", "redis-cli", "ping"]
    interval: 5s
    timeout: 3s
    retries: 10
```

Redis has no persistent volume in v0.8.

This is intentional. Redis content is disposable and rebuildable from PostgreSQL.

The existing PostgreSQL and Kafka services remain unchanged except for any formatting needed to add Redis cleanly.

## Redis persistence stance

v0.8 does not rely on Redis RDB/AOF persistence.

Expected behavior:

```text
Redis process loss
or
FLUSHALL
or
container recreation
=> cache loss only
=> no banking-data loss
```

The cache repopulates on subsequent reads/replays.

## Actuator health behavior

Redis is not a critical availability dependency in v0.8.

Therefore the global application health result must not become `DOWN` solely because Redis is unavailable.

Implementation should disable or isolate the Redis health contributor from the primary readiness decision, for example with the appropriate Spring Boot Actuator Redis health configuration.

The exact property must be verified against Spring Boot 3.5.6 during implementation.

PostgreSQL remains a critical dependency.

## Logging and privacy

Redis/cache logs may contain sanitized technical information such as:

- cache name;
- cache operation (`GET`, `PUT`, `EVICT`);
- exception type;
- a non-sensitive internal UUID where necessary;
- hashed idempotency key digest if needed for debugging.

Redis/cache logs must not contain:

```text
raw Idempotency-Key
response_body
balance
balanceBefore
balanceAfter
document
email
financial request payload
full Redis value
```

Do not log a serialized replay pointer value.

## Metrics and observability scope

v0.8 requires sanitized operational logging for cache degradation.

Detailed cache hit/miss ratios, Redis latency dashboards, alerts, and production observability are deferred to the CoreBank observability milestone unless trivial framework metrics are already available without expanding scope.

## Security considerations

v0.8 applies data minimization to Redis:

- only safe summary projections are cached;
- PII is excluded from CustomerSummary;
- balance data is excluded from AccountSummary;
- raw idempotency keys are hashed before key construction;
- Redis does not store complete financial replay bodies;
- secrets/credentials are supplied through environment variables, never hard-coded.

Production network controls, TLS, Redis ACLs, and managed-service configuration belong to deployment hardening/AWS work unless required earlier by the chosen environment.

## Testing strategy

### Unit tests

Cover:

- CustomerSummary mapping excludes document/email;
- AccountSummary mapping excludes balance/version/updatedAt;
- cache-key prefix composition;
- idempotency key hashing is deterministic lower-case SHA-256;
- replay-pointer validation;
- malformed/stale replay pointer behavior;
- fail-open error handler behavior;
- configurable TTL binding.

### Redis integration tests

Use a real Redis container, preferably Testcontainers `GenericContainer` with `redis:7-alpine`.

Cover:

- CustomerSummary first request populates Redis;
- subsequent CustomerSummary request can be served from cache;
- stored CustomerSummary does not contain document/email;
- AccountSummary first request populates Redis;
- subsequent AccountSummary request can be served from cache;
- stored AccountSummary does not contain balance;
- five-minute summary TTL is configured/applied;
- replay pointer receives one-hour TTL;
- replay key contains SHA-256 digest instead of raw Idempotency-Key;
- replay pointer does not contain response body or balance fields;
- malformed cached values fall back safely.

### PostgreSQL + Redis integration tests

Cover:

- Redis miss falls back to PostgreSQL;
- full Customer endpoint continues to use authoritative complete data;
- full Account endpoint continues to return authoritative balance;
- completed idempotent record can repopulate missing Redis pointer;
- Redis pointer hit still verifies PostgreSQL record;
- stale pointer never causes command re-execution;
- Redis deletion/flush does not alter financial correctness.

### Fail-open integration tests

Cover Redis unavailable before and during operations:

```text
Customer summary -> PostgreSQL fallback
Account summary -> PostgreSQL fallback
Deposit -> succeeds/fails only by PostgreSQL/business rules
Withdrawal -> succeeds/fails only by PostgreSQL/business rules
Transfer -> succeeds/fails only by PostgreSQL/business rules
Idempotent replay -> remains correct through PostgreSQL
```

Redis outage must never create duplicate financial operations.

### Transaction-boundary tests

Prove:

1. newly completed idempotency pointer is not written before PostgreSQL commit;
2. PostgreSQL rollback produces no durable Redis pointer for that attempted completion;
3. after successful commit, best-effort pointer population occurs;
4. Redis write failure after commit does not roll back the committed financial transaction.

### Cache-loss recovery test

Explicit scenario:

1. create Customer;
2. create Account;
3. execute an idempotent financial operation;
4. populate CustomerSummary, AccountSummary, and replay pointer;
5. flush Redis or recreate the Redis container;
6. repeat summary reads;
7. repeat the same Idempotency-Key;
8. verify summaries rebuild;
9. verify PostgreSQL returns the prior idempotent response;
10. verify the financial operation was not executed a second time.

## Acceptance criteria

v0.8 is acceptable only when all of the following are true:

1. `GET /api/v1/customers/{id}/summary` exists;
2. CustomerSummary is Redis cache-aside with default TTL 5 minutes;
3. CustomerSummary contains no document or email;
4. `GET /api/v1/accounts/{id}/summary` exists;
5. AccountSummary is Redis cache-aside with default TTL 5 minutes;
6. AccountSummary contains no balance;
7. existing complete Customer endpoint remains PostgreSQL-authoritative;
8. existing complete Account endpoint remains PostgreSQL-authoritative;
9. Redis idempotency cache stores only completed replay pointers;
10. replay-pointer default TTL is 1 hour;
11. original Idempotency-Key never appears in the Redis key;
12. full financial response body never appears in Redis;
13. `IN_PROGRESS` and idempotency locking remain PostgreSQL-only;
14. a newly completed replay pointer is written only after PostgreSQL commit;
15. Redis outage does not make valid financial operations fail solely because Redis is down;
16. Redis outage does not duplicate an idempotent financial operation;
17. complete Redis cache loss causes no banking-data loss;
18. Docker Compose includes ephemeral Redis;
19. global health/readiness is not `DOWN` solely because optional Redis is unavailable;
20. tests cover cache hit, miss, TTL, fail-open, corruption/staleness, after-commit population, and full cache loss;
21. README documents Redis as a disposable non-authoritative performance layer;
22. final regression verification reports `BUILD SUCCESS` with zero test failures/errors.

## Regression gate

Final release verification:

```text
mvn clean verify
```

v0.8 is not GREEN until fresh output proves `BUILD SUCCESS` with zero reported failures/errors.

Do not infer GREEN from prior v0.7 output.

## Versioning and documentation

During implementation:

- bump Maven project version from `0.7.0` to `0.8.0` at the appropriate release stage;
- update `info.app.version` to `0.8.0`;
- update README architecture, Redis behavior, local startup, and roadmap;
- document the key invariant that Redis loss must not cause financial-data loss.

No Flyway migration is expected solely for Redis introduction unless implementation uncovers a concrete PostgreSQL schema need. Any such migration must be justified before addition.

## Release workflow

Branch:

```text
feature/corebank-v0.8
```

Workflow:

1. keep implementation on the feature branch;
2. implement in larger checkpoints, not tiny repetitive test loops;
3. run focused tests during checkpoints;
4. run final local `mvn clean verify` only when the implementation checkpoint is complete;
5. review the full diff against this specification;
6. open a PR to `main`;
7. never merge without explicit user approval;
8. after approval, use the chosen merge strategy;
9. synchronize local `main`;
10. create the final v0.8 release tag only after the merged commit is verified.

## Final architectural statement

CoreBank v0.8 treats Redis as disposable acceleration infrastructure.

The defining invariant is:

> Redis OFF = CoreBank remains correct.

PostgreSQL continues to guarantee the bank. Redis only makes selected safe reads and completed idempotency lookups faster.
