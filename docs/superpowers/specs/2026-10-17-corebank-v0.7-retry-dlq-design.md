# CoreBank v0.7 — Retry + DLQ Design

## Status

Approved architectural design for CoreBank v0.7.

## Context

CoreBank v0.6 introduced asynchronous financial event publication through a PostgreSQL Transactional Outbox and Apache Kafka. Financial state, ledger state, idempotency state, and the outbox row are committed atomically in PostgreSQL. Kafka publication occurs later, outside the financial transaction, and an outbox row is marked `PUBLISHED` only after Kafka acknowledgement.

The v0.6 publisher intentionally had no retry policy, no backoff, no max-attempt policy, and no dead-letter flow. A publication failure left the event `PENDING`, and the next scheduler cycle attempted the oldest pending row again. That behavior is correct for the initial outbox milestone but is insufficient for production-style fault handling because one poison or persistently failing event can block progress and because retry timing is not durable or observable.

CoreBank v0.7 adds durable retry scheduling and a dead-letter pipeline while preserving the v0.6 transactional boundary: a Kafka outage must never invalidate a financial transaction that already committed successfully.

## Goals

CoreBank v0.7 must:

1. Persist retry state in PostgreSQL so application restarts and deployments do not lose retry progress.
2. Retry transient publication failures with explicit backoff.
3. Stop retrying the primary outbox event after five failed attempts.
4. Send permanently failed events to a durable dead-letter pipeline.
5. Classify failures as retriable or non-retriable.
6. Send non-retriable failures directly to dead-letter handling without wasting five attempts.
7. Keep the dead-letter handoff transactionally safe through PostgreSQL rather than using a direct dual-write to Kafka.
8. Publish dead-letter records to a dedicated Kafka topic.
9. Preserve at-least-once semantics for both the primary topic and the dead-letter topic.
10. Keep error information sanitized and bounded in the database.
11. Preserve concurrent publisher safety using PostgreSQL row locking and `SKIP LOCKED`.
12. Avoid introducing Redis, JWT/RBAC, administrative redrive, or service extraction in this release.

## Non-goals

The following are explicitly out of scope for v0.7:

- Manual or automatic redrive of dead-lettered business events.
- Administrative REST endpoints for retry or DLQ management.
- Exactly-once Kafka delivery.
- Distributed transactions between PostgreSQL and Kafka.
- Kafka retry topics for the primary event stream.
- A "DLQ of the DLQ".
- Redis-based scheduling or locks.
- Consumer-side idempotency.
- JWT/RBAC.
- Frontend work.

A dead-lettered primary event is terminal in v0.7. Future redrive must be introduced as a separate auditable feature.

## Architectural principle

PostgreSQL remains the transactional system of record for publication state.

No code path may require an atomic commit across PostgreSQL and Kafka.

The invariant remains:

> A valid financial operation must succeed or fail based on the financial PostgreSQL transaction, not on Kafka availability.

The v0.7 dead-letter design follows the same rule. When a primary outbox event is exhausted or found to be non-retriable, the primary event is marked dead-lettered and a durable dead-letter row is created in the same PostgreSQL transaction. Kafka publication of that dead-letter row occurs later.

## Primary event state machine

`outbox_events.status` is extended from:

- `PENDING`
- `PUBLISHED`

to:

- `PENDING`
- `PUBLISHED`
- `DEAD_LETTERED`

State transitions:

```text
PENDING --Kafka ACK--> PUBLISHED
PENDING --retriable failure, attempts < 5--> PENDING
PENDING --retriable failure, attempt = 5--> DEAD_LETTERED
PENDING --non-retriable failure--> DEAD_LETTERED
```

`PUBLISHED` and `DEAD_LETTERED` are terminal states for the primary outbox in v0.7.

## Retry policy

The primary publisher uses durable retry state stored in PostgreSQL.

Maximum failed publication attempts:

```text
maxAttempts = 5
```

For retriable failures, the schedule is:

```text
1st failure -> next attempt in 2 seconds
2nd failure -> next attempt in 5 seconds
3rd failure -> next attempt in 15 seconds
4th failure -> next attempt in 30 seconds
5th failure -> DEAD_LETTERED
```

The retry schedule is persisted through `next_attempt_at` rather than implemented using in-memory `Spring Retry` state. Restarting the process does not reset counters or backoff timing.

## Primary outbox schema changes

A Flyway migration extends `outbox_events` with:

```text
attempt_count       INTEGER NOT NULL DEFAULT 0
next_attempt_at     TIMESTAMPTZ NOT NULL
last_error_type     VARCHAR(128) NULL
last_error_message  VARCHAR(500) NULL
```

Migration compatibility requirement:

- Existing v0.6 rows must remain valid.
- Existing `PENDING` rows receive an immediately eligible `next_attempt_at` value.
- Existing `PUBLISHED` rows remain terminal and require no retry behavior.
- `attempt_count` starts at zero for migrated rows.

Recommended migration initialization:

```sql
attempt_count = 0
next_attempt_at = created_at
```

or an equivalent value that makes legacy pending rows eligible without artificial delay.

A check constraint should prevent negative `attempt_count` values.

## Selecting eligible primary events

The repository no longer selects simply the oldest pending row. It selects the oldest eligible retry row:

```sql
SELECT ...
FROM outbox_events
WHERE status = 'PENDING'
  AND next_attempt_at <= NOW()
ORDER BY next_attempt_at, created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

The exact native PostgreSQL clause order used by the implementation must be syntactically valid and covered by integration tests.

This keeps concurrent workers safe while allowing newer eligible events to progress when an older event is waiting for its backoff window.

## Failure classification

Publication failures are divided into two categories.

### Retriable failures

Examples include:

- broker unavailable;
- temporary network failure;
- timeout while waiting for Kafka acknowledgement;
- transient Kafka client errors where retry can reasonably succeed later.

A retriable failure:

1. increments `attempt_count`;
2. stores sanitized error metadata;
3. either schedules `next_attempt_at` according to the retry table, or dead-letters the event if the new attempt count reaches five.

### Non-retriable failures

Examples include:

- deterministic JSON serialization failure;
- structurally invalid event state that cannot be repaired by waiting;
- contract construction failure known to repeat identically.

A non-retriable failure is not retried five times. It moves directly to `DEAD_LETTERED` and creates a durable `dead_letter_events` row in the same PostgreSQL transaction.

The implementation should classify known deterministic failures explicitly. Unknown runtime failures should default conservatively according to the failure taxonomy defined in code and tests; the classification must not be an uncontrolled string comparison against exception messages.

## Error persistence

The database must not persist full stack traces.

Persist only bounded, sanitized metadata:

```text
last_error_type
last_error_message
```

Rules:

- `last_error_type` contains a stable exception/error class name or normalized category.
- `last_error_message` is sanitized and limited to 500 characters.
- no event payload is appended to the error text;
- no secrets, credentials, connection strings, stack traces, or request bodies are persisted;
- complete stack traces may be written to application logs where appropriate.

When an event succeeds after prior failures, v0.7 may keep prior error metadata for auditability or clear it when marking `PUBLISHED`; the implementation plan must choose one behavior and test it consistently. The preferred behavior is to retain `attempt_count` but clear active error fields on successful publication so row state reflects the final outcome while historical attempt count remains observable.

## Dead-letter persistence model

CoreBank v0.7 introduces a new PostgreSQL table:

```text
dead_letter_events
```

Required fields:

```text
id                  UUID PRIMARY KEY
original_event_id   UUID NOT NULL UNIQUE
event_type          VARCHAR(64) NOT NULL
event_version       INTEGER NOT NULL
aggregate_type      VARCHAR(64) NOT NULL
aggregate_id        UUID NOT NULL
correlation_id      UUID NOT NULL
message_key         VARCHAR(128) NOT NULL
payload             JSONB NOT NULL
attempt_count       INTEGER NOT NULL
last_error_type     VARCHAR(128) NOT NULL
last_error_message  VARCHAR(500) NULL
failed_at           TIMESTAMPTZ NOT NULL
status              VARCHAR(16) NOT NULL
next_attempt_at     TIMESTAMPTZ NOT NULL
publish_attempts    INTEGER NOT NULL DEFAULT 0
created_at          TIMESTAMPTZ NOT NULL
published_at        TIMESTAMPTZ NULL
```

`original_event_id` is unique so one primary outbox event cannot generate duplicate dead-letter rows through repeated execution or rollback/retry edges.

The DLQ payload is a durable snapshot of the original event contract plus failure metadata. It must not introduce free-form transaction descriptions, idempotency keys, customer PII, balances, or HTTP payloads that were intentionally excluded from the v0.6 financial event contract.

## Atomic primary dead-letter transition

The transition of a primary event to `DEAD_LETTERED` and creation of `dead_letter_events` must occur in the same PostgreSQL transaction.

Pseudo-flow:

```text
BEGIN
  lock eligible outbox row
  classify failure
  update outbox_events -> DEAD_LETTERED
  insert dead_letter_events -> PENDING
COMMIT
```

If the transaction rolls back, neither state change is committed.

The implementation must not publish directly to the Kafka DLQ inside this transaction.

## Dead-letter Kafka topic

Dedicated topic:

```text
corebank.financial-events.dlq.v1
```

The topic is versioned independently from the primary topic.

Recommended local-development configuration:

- partitions: 3
- replication factor: 1

The DLQ message key should remain the original `message_key` so related events preserve the same partitioning intent as the primary financial stream.

## Dead-letter envelope

The DLQ Kafka message should be explicit and versioned rather than serializing the JPA entity directly.

Recommended envelope:

```json
{
  "deadLetterId": "uuid",
  "originalEventId": "uuid",
  "eventType": "TRANSFER_COMPLETED",
  "eventVersion": 1,
  "aggregateType": "TRANSFER",
  "aggregateId": "uuid",
  "correlationId": "uuid",
  "failedAt": "2026-10-17T00:00:00Z",
  "attemptCount": 5,
  "errorType": "TimeoutException",
  "errorMessage": "Kafka publish failed after broker timeout",
  "payload": {}
}
```

The exact Java record/class naming may vary, but the contract must be explicit, deterministic, and tested.

## Dead-letter publisher state machine

`dead_letter_events.status` has two states:

- `PENDING`
- `PUBLISHED`

State transition:

```text
PENDING --Kafka DLQ ACK--> PUBLISHED
```

A DLQ Kafka failure does not create another dead-letter record and does not introduce a terminal failed state in v0.7.

## DLQ publisher retry policy

The dead-letter publisher retries indefinitely because PostgreSQL already safely retains the record and there is no secondary DLQ.

Backoff:

```text
1st DLQ publication failure -> 5 seconds
2nd -> 15 seconds
3rd -> 30 seconds
4th and later -> 60 seconds
```

The delay remains capped at 60 seconds for all subsequent attempts.

State must be durable through:

- `publish_attempts`;
- `next_attempt_at`;
- bounded/sanitized publication error metadata if the implementation chooses to store separate DLQ-publication error fields.

If separate DLQ publication error fields are added, they must follow the same sanitization rules as the primary outbox.

The implementation plan should prefer minimal schema: reuse fields only when their semantics remain unambiguous; otherwise add clearly named DLQ publication error fields.

## Selecting eligible dead-letter rows

The DLQ repository uses an eligible-row query analogous to the primary publisher:

```sql
WHERE status = 'PENDING'
  AND next_attempt_at <= NOW()
ORDER BY next_attempt_at, created_at
LIMIT 1
FOR UPDATE SKIP LOCKED
```

Each claim/publish operation executes in its own `REQUIRES_NEW` transaction so independent workers do not share publication state.

## Publisher transaction semantics

### Primary publisher

For one primary event:

- open `REQUIRES_NEW` transaction;
- claim one eligible row with row lock;
- serialize explicit envelope;
- send to primary Kafka topic and wait for acknowledgement;
- on success, mark `PUBLISHED` and commit;
- on retriable failure, update retry state or dead-letter at attempt five and commit that failure state;
- on non-retriable failure, dead-letter immediately and commit;
- preserve interrupt status for `InterruptedException`.

Unlike v0.6, an expected publication failure must not always be represented by rolling back the entire worker transaction, because v0.7 needs the retry attempt and scheduling decision to persist. Infrastructure/database failures while persisting that decision should still roll back normally.

### DLQ publisher

For one dead-letter event:

- open `REQUIRES_NEW` transaction;
- claim one eligible row;
- serialize explicit DLQ envelope;
- publish to `corebank.financial-events.dlq.v1` and wait for acknowledgement;
- on success, mark `PUBLISHED` and set `published_at`;
- on Kafka failure, increment durable DLQ publish attempts, schedule the next attempt, and commit the retry state.

## At-least-once semantics

The existing at-least-once caveat remains.

For the primary topic:

```text
Kafka ACK succeeds
process crashes before PostgreSQL commit
=> primary event may be published again
```

For the DLQ topic:

```text
Kafka DLQ ACK succeeds
process crashes before dead_letter_events status commit
=> dead-letter message may be published again
```

Consumers must use stable identifiers for deduplication when required:

- primary stream: `eventId`;
- DLQ stream: `deadLetterId` and/or `originalEventId` according to consumer purpose.

Exactly-once delivery is not claimed.

## Batch behavior and poison-event isolation

In v0.6 the batch intentionally stopped after the first failure to avoid hammering the same oldest pending row.

In v0.7, once a retriable failure is committed with `next_attempt_at` in the future, that row is temporarily ineligible. Therefore subsequent eligible events can progress without being blocked by the failed row.

Recommended v0.7 behavior:

- continue the current batch after a handled publication failure whose retry/dead-letter state was successfully persisted;
- stop the batch only when a database/infrastructure failure prevents safe persistence of publication state, or when no eligible row remains.

This change prevents one failing event from starving unrelated events.

## Scheduler model

Keep the scheduler simple and database-driven.

Primary scheduler:

- wakes at a short fixed interval;
- asks the publisher for eligible rows;
- eligibility is determined by `next_attempt_at`, not by sleeping inside worker threads.

DLQ scheduler:

- independent scheduled publisher;
- same principle: no long thread sleeps, only durable `next_attempt_at` state.

The exact fixed-delay defaults remain configuration properties and should be conservative for local development and tests.

## Configuration

Recommended configuration properties:

```text
corebank.outbox.max-attempts=5
corebank.outbox.retry-delays=2s,5s,15s,30s
corebank.outbox.batch-size=100
corebank.outbox.fixed-delay-ms=2000

corebank.kafka.topic.financial-events=corebank.financial-events.v1
corebank.kafka.topic.financial-events-dlq=corebank.financial-events.dlq.v1

corebank.dlq.retry-delays=5s,15s,30s,60s
corebank.dlq.max-delay=60s
corebank.dlq.batch-size=100
corebank.dlq.fixed-delay-ms=2000
```

Implementation may model duration lists differently if Spring binding is clearer, but policy values must remain externally configurable and tested.

## Logging and observability

v0.7 does not implement the full observability roadmap, but logs must support operational diagnosis without leaking payloads.

Primary publication logs should include identifiers such as:

- `eventId`;
- `eventType`;
- `aggregateId`;
- `attemptCount`;
- `nextAttemptAt` when applicable;
- final status.

Dead-letter logs should include:

- `deadLetterId`;
- `originalEventId`;
- publication attempt count;
- next attempt time;
- final status.

Do not log the full payload as part of retry error handling.

## Database indexing

Indexes should support the eligibility scans.

Recommended partial indexes:

```sql
CREATE INDEX ... ON outbox_events (next_attempt_at, created_at)
WHERE status = 'PENDING';

CREATE INDEX ... ON dead_letter_events (next_attempt_at, created_at)
WHERE status = 'PENDING';
```

The existing v0.6 pending index should be replaced or adapted if redundant.

## Concurrency requirements

The implementation must prove:

1. Two primary workers cannot publish the same locked row concurrently under normal execution.
2. A worker can skip a primary row that is currently locked and claim the next eligible row.
3. A row waiting for backoff does not block another eligible row.
4. Two DLQ workers cannot publish the same dead-letter row concurrently under normal execution.
5. Unique `original_event_id` prevents duplicate dead-letter row creation.

PostgreSQL `FOR UPDATE SKIP LOCKED` remains the concurrency primitive.

## Failure matrix

### Primary publication succeeds

Result:

- outbox -> `PUBLISHED`;
- `published_at` populated;
- no dead-letter row.

### Retriable failure, attempts 1-4

Result:

- outbox remains `PENDING`;
- `attempt_count` incremented;
- `next_attempt_at` scheduled;
- sanitized error metadata saved;
- no dead-letter row.

### Retriable failure, attempt 5

Result in one PostgreSQL transaction:

- outbox -> `DEAD_LETTERED`;
- `attempt_count = 5`;
- final error metadata persisted;
- one `dead_letter_events` row -> `PENDING`.

### Non-retriable failure

Result in one PostgreSQL transaction:

- outbox -> `DEAD_LETTERED` immediately;
- one dead-letter row created;
- no unnecessary repeated primary attempts.

### DLQ Kafka unavailable

Result:

- dead-letter row remains `PENDING`;
- `publish_attempts` incremented;
- `next_attempt_at` follows 5s/15s/30s/60s/capped 60s;
- no secondary dead-letter record.

### Database failure while recording retry/dead-letter state

Result:

- transaction rolls back;
- event remains in its prior durable state;
- scheduler may encounter it again later;
- do not falsely mark it `PUBLISHED` or `DEAD_LETTERED`.

## Testing strategy

v0.7 requires unit and integration coverage.

### Unit tests

Cover:

- retry-delay selection for attempts 1-4;
- fifth attempt dead-letter decision;
- non-retriable classification;
- message sanitization/truncation;
- primary event state transitions;
- dead-letter event state transitions;
- DLQ backoff with 60-second cap;
- publisher batch continuation after a handled failure.

### PostgreSQL integration tests

Cover:

- Flyway migration from v0.6-compatible state;
- new constraints/defaults/indexes;
- eligible-row query respects `next_attempt_at`;
- `SKIP LOCKED` behavior;
- atomic primary dead-letter transition;
- unique `original_event_id`;
- retry state persists across separate transactions.

### Kafka integration tests

Cover:

- transient primary Kafka failure schedules retry;
- later successful retry publishes exactly the same event contract and marks `PUBLISHED`;
- attempt five creates a dead-letter row;
- deterministic non-retriable failure dead-letters immediately;
- dead-letter row publishes to `corebank.financial-events.dlq.v1`;
- DLQ Kafka failure persists its own retry schedule;
- later DLQ recovery marks `PUBLISHED`;
- primary and DLQ message payloads exclude sensitive/free-form fields.

### Regression gate

Final local gate remains:

```text
mvn clean verify
```

The release is not GREEN until fresh output proves `BUILD SUCCESS` with zero reported test failures/errors.

## Release workflow

Implementation must use:

```text
feature/corebank-v0.7
```

No direct changes to `main`.

After implementation:

1. run final local `mvn clean verify`;
2. review full branch diff against this specification;
3. open PR to `main`;
4. do not merge without explicit user approval;
5. squash merge after approval;
6. create annotated tag `v0.7.0` only after merge verification.

## Deferred work

Potential future work, not part of v0.7:

- authenticated administrative DLQ inspection;
- manual redrive with audit history;
- redrive authorization through RBAC;
- metrics and alert thresholds for pending/retry/dead-letter counts;
- consumer-side deduplication store;
- Kafka retry-topic architecture if service extraction later justifies it.

## Acceptance criteria

CoreBank v0.7 is complete only when all of the following are true:

1. Primary retries are durable across restarts.
2. Retry timing follows 2s, 5s, 15s, 30s.
3. A retriable event moves to `DEAD_LETTERED` on the fifth failed primary publication attempt.
4. Non-retriable failures move directly to `DEAD_LETTERED`.
5. Primary dead-letter state and dead-letter-row creation are atomic in PostgreSQL.
6. DLQ publication uses `corebank.financial-events.dlq.v1`.
7. DLQ publication retries indefinitely with 5s, 15s, 30s, then capped 60s backoff.
8. No "DLQ of DLQ" exists.
9. No redrive feature exists in v0.7.
10. Error persistence is sanitized and bounded; no stack traces are stored in database columns.
11. `SKIP LOCKED` concurrency remains correct for both publishers.
12. At-least-once semantics are documented and tested where practical.
13. Financial operations remain independent of Kafka availability.
14. Fresh `mvn clean verify` evidence is GREEN before PR merge.
