# CoreBank v0.7 — Retry + DLQ Design

## Status

Approved architectural design, pending final user review of this written specification.

## Context

CoreBank v0.6 introduced Apache Kafka publication through a PostgreSQL Transactional Outbox. Financial state, ledger state, idempotency state, and the outbox row commit atomically in PostgreSQL. Kafka publication occurs later, so Kafka availability never decides whether a valid financial transaction commits.

v0.7 adds durable retry scheduling and a dead-letter pipeline without changing that boundary.

## Goals

v0.7 must:

1. persist retry state in PostgreSQL;
2. retry transient Kafka failures with explicit backoff;
3. stop primary publication after five failed attempts;
4. dead-letter deterministic failures immediately;
5. create the dead-letter record atomically with the primary `DEAD_LETTERED` transition;
6. publish dead-letter records asynchronously to a dedicated Kafka topic;
7. retry DLQ publication indefinitely with bounded backoff;
8. preserve `FOR UPDATE SKIP LOCKED` concurrency;
9. persist only sanitized, bounded error metadata;
10. preserve at-least-once semantics.

## Non-goals

Not part of v0.7:

- redrive/reprocessing of dead-lettered business events;
- admin endpoints;
- exactly-once Kafka delivery;
- XA/distributed transactions;
- Kafka retry topics for the primary stream;
- a DLQ of the DLQ;
- Redis;
- JWT/RBAC;
- frontend work.

`DEAD_LETTERED` is terminal for a primary outbox event in v0.7.

## Architectural invariant

PostgreSQL remains the transactional source of truth for publication state.

> Kafka failure must never invalidate a financial transaction that has already committed successfully.

No code path requires an atomic PostgreSQL + Kafka commit.

## Primary outbox state machine

`outbox_events.status` becomes:

- `PENDING`
- `PUBLISHED`
- `DEAD_LETTERED`

Transitions:

```text
PENDING --Kafka ACK--> PUBLISHED
PENDING --retriable failure, attempts < 5--> PENDING
PENDING --retriable failure, attempt = 5--> DEAD_LETTERED
PENDING --non-retriable failure--> DEAD_LETTERED
```

`PUBLISHED` and `DEAD_LETTERED` are terminal.

## Primary retry policy

Maximum failed primary publication attempts:

```text
maxAttempts = 5
```

Backoff for retriable failures:

```text
1st failure -> retry in 2s
2nd failure -> retry in 5s
3rd failure -> retry in 15s
4th failure -> retry in 30s
5th failure -> DEAD_LETTERED
```

Retry state is durable. No in-memory `@Retryable` policy is the source of truth.

## Primary schema changes

Flyway extends `outbox_events` with:

```text
attempt_count       INTEGER NOT NULL DEFAULT 0
next_attempt_at     TIMESTAMPTZ NOT NULL
last_error_type     VARCHAR(128) NULL
last_error_message  VARCHAR(500) NULL
```

Migration requirements:

- v0.6 rows remain valid;
- legacy `PENDING` rows become immediately eligible;
- legacy `PUBLISHED` rows remain terminal;
- `attempt_count` initializes to zero;
- negative attempt counts are rejected.

Recommended initialization:

```text
attempt_count = 0
next_attempt_at = created_at
```

## Eligible primary-event query

The repository selects only due events:

```sql
WHERE status = 'PENDING'
  AND next_attempt_at <= NOW()
ORDER BY next_attempt_at, created_at
LIMIT 1
FOR UPDATE SKIP LOCKED
```

The implementation must use PostgreSQL-valid clause ordering and prove it with integration tests.

A pending event whose backoff has not expired does not block another eligible event.

## Failure classification

### Retriable

Examples:

- broker unavailable;
- network failure;
- timeout waiting for Kafka acknowledgement;
- transient Kafka client failure.

A retriable failure increments `attempt_count`, persists sanitized error data, and either schedules `next_attempt_at` or dead-letters on attempt five.

### Non-retriable

Examples:

- deterministic JSON serialization failure;
- structurally invalid event state;
- deterministic contract-construction failure.

A non-retriable failure goes directly to `DEAD_LETTERED` without consuming five retries.

Classification must be type/category based, never string matching on exception messages.

Unknown failures must follow an explicit conservative default defined in code and tests.

## Error persistence

Persist only:

```text
last_error_type
last_error_message
```

Rules:

- no stack traces in database columns;
- no payload concatenated into messages;
- no credentials, connection strings, request bodies, or secrets;
- message limited to 500 characters;
- full stack trace may appear in application logs.

If a primary event later succeeds after one or more retries:

- `attempt_count` is retained for auditability;
- `last_error_type` is cleared;
- `last_error_message` is cleared;
- final status becomes `PUBLISHED`.

This behavior is mandatory and must be tested.

## Dead-letter persistence

Introduce `dead_letter_events`:

```text
id                         UUID PRIMARY KEY
original_event_id          UUID NOT NULL UNIQUE
event_type                 VARCHAR(64) NOT NULL
event_version              INTEGER NOT NULL
aggregate_type             VARCHAR(64) NOT NULL
aggregate_id               UUID NOT NULL
correlation_id             UUID NOT NULL
message_key                VARCHAR(128) NOT NULL
payload                    JSONB NOT NULL
attempt_count              INTEGER NOT NULL
last_error_type            VARCHAR(128) NOT NULL
last_error_message         VARCHAR(500) NULL
failed_at                  TIMESTAMPTZ NOT NULL
status                     VARCHAR(16) NOT NULL
publish_attempts           INTEGER NOT NULL DEFAULT 0
next_attempt_at            TIMESTAMPTZ NOT NULL
last_publish_error_type    VARCHAR(128) NULL
last_publish_error_message VARCHAR(500) NULL
created_at                 TIMESTAMPTZ NOT NULL
published_at               TIMESTAMPTZ NULL
```

`original_event_id` is unique so one primary event cannot create multiple durable dead-letter rows.

The dead-letter row contains the original safe event payload plus bounded failure metadata. It must not add free-form transaction descriptions, idempotency keys, balances, customer PII, HTTP request bodies, or other fields excluded from the v0.6 event contract.

## Atomic dead-letter transition

When a primary event must be dead-lettered, the following happen in one PostgreSQL transaction:

```text
outbox_events.status = DEAD_LETTERED
+ final primary failure metadata
+ INSERT dead_letter_events(status=PENDING)
```

If the transaction rolls back, neither the primary transition nor the dead-letter row is committed.

The Kafka DLQ is never published directly inside this transition.

## DLQ Kafka topic

Dedicated topic:

```text
corebank.financial-events.dlq.v1
```

Local-development defaults:

```text
partitions = 3
replication factor = 1
```

The Kafka key remains the original `message_key`.

## DLQ envelope

Use an explicit versioned contract, never JPA serialization. Minimum fields:

```json
{
  "deadLetterId": "uuid",
  "originalEventId": "uuid",
  "eventType": "TRANSFER_COMPLETED",
  "eventVersion": 1,
  "aggregateType": "TRANSFER",
  "aggregateId": "uuid",
  "correlationId": "uuid",
  "failedAt": "2026-10-17T00:00:00Z",
  "attemptCount": 5,
  "errorType": "TimeoutException",
  "errorMessage": "Kafka publish failed after broker timeout",
  "payload": {}
}
```

The Java representation may be a record/class, but the serialized contract must be deterministic and tested.

## DLQ state machine

`dead_letter_events.status`:

- `PENDING`
- `PUBLISHED`

Transition:

```text
PENDING --DLQ Kafka ACK--> PUBLISHED
```

No terminal failed state and no secondary DLQ are introduced in v0.7.

## DLQ retry policy

DLQ publication retries indefinitely.

```text
1st failure -> 5s
2nd failure -> 15s
3rd failure -> 30s
4th+ failure -> 60s
```

The delay is capped at 60 seconds forever after.

On DLQ publication failure:

- increment `publish_attempts`;
- set `next_attempt_at`;
- persist sanitized `last_publish_error_type`;
- persist sanitized/truncated `last_publish_error_message`;
- keep status `PENDING`.

On successful DLQ publication:

- retain `publish_attempts` for auditability;
- clear `last_publish_error_type`;
- clear `last_publish_error_message`;
- set `published_at`;
- set status `PUBLISHED`.

## Eligible DLQ query

```sql
WHERE status = 'PENDING'
  AND next_attempt_at <= NOW()
ORDER BY next_attempt_at, created_at
LIMIT 1
FOR UPDATE SKIP LOCKED
```

Each claim/publish operation uses its own `REQUIRES_NEW` transaction.

## Primary publisher transaction semantics

For one eligible primary row:

1. begin `REQUIRES_NEW` transaction;
2. claim row with `FOR UPDATE SKIP LOCKED`;
3. serialize explicit primary envelope;
4. send to primary Kafka topic and wait for ACK;
5. on success: mark `PUBLISHED`, clear active error fields, commit;
6. on retriable failure: persist retry state or atomic dead-letter transition, commit;
7. on non-retriable failure: atomic dead-letter transition, commit;
8. preserve interrupt status for interruption paths.

Expected Kafka publication failures no longer always roll back the worker transaction because v0.7 must persist the retry/dead-letter decision. Database failures while persisting state still roll back normally.

## DLQ publisher transaction semantics

For one eligible dead-letter row:

1. begin `REQUIRES_NEW` transaction;
2. claim row;
3. serialize explicit DLQ envelope;
4. publish to `corebank.financial-events.dlq.v1` and wait for ACK;
5. on success: mark `PUBLISHED`, clear DLQ publication error fields, commit;
6. on Kafka failure: persist `publish_attempts`, next backoff time, and sanitized DLQ publication error metadata, then commit.

## Batch behavior

v0.7 changes the v0.6 poison-event behavior.

After a handled primary publication failure is durably persisted, the failed row becomes either temporarily ineligible or terminal. Therefore the publisher may continue processing other eligible rows in the same batch.

Stop a batch only when:

- no eligible row remains; or
- a database/infrastructure problem prevents safe persistence of publication state.

The same principle applies to the DLQ publisher.

## Scheduler model

Primary and DLQ schedulers are independent and database-driven.

No worker thread sleeps for the backoff duration. `next_attempt_at` controls eligibility.

Recommended externally configurable defaults:

```text
corebank.outbox.max-attempts=5
corebank.outbox.retry-delays=2s,5s,15s,30s
corebank.outbox.batch-size=100
corebank.outbox.fixed-delay-ms=2000

corebank.kafka.topic.financial-events=corebank.financial-events.v1
corebank.kafka.topic.financial-events-dlq=corebank.financial-events.dlq.v1

corebank.dlq.retry-delays=5s,15s,30s,60s
corebank.dlq.max-delay=60s
corebank.dlq.batch-size=100
corebank.dlq.fixed-delay-ms=2000
```

Exact Spring binding may differ, but policy values remain configurable.

## At-least-once semantics

Primary stream:

```text
Kafka ACK succeeds
process crashes before PostgreSQL status commit
=> event may be published again
```

DLQ stream:

```text
DLQ Kafka ACK succeeds
process crashes before dead_letter_events status commit
=> DLQ message may be published again
```

Stable deduplication identifiers:

- primary: `eventId`;
- DLQ: `deadLetterId`, with `originalEventId` available for correlation.

Exactly-once delivery is not claimed.

## Logging

Primary logs may include:

- `eventId`;
- `eventType`;
- `aggregateId`;
- `attemptCount`;
- `nextAttemptAt`;
- status.

DLQ logs may include:

- `deadLetterId`;
- `originalEventId`;
- `publishAttempts`;
- `nextAttemptAt`;
- status.

Do not log full event payloads in retry/DLQ error paths.

## Indexing

Use partial eligibility indexes:

```sql
CREATE INDEX ... ON outbox_events (next_attempt_at, created_at)
WHERE status = 'PENDING';

CREATE INDEX ... ON dead_letter_events (next_attempt_at, created_at)
WHERE status = 'PENDING';
```

Replace/adapt the v0.6 pending index if it becomes redundant.

## Concurrency requirements

Tests must prove:

1. two primary workers do not concurrently claim the same row;
2. a locked primary row can be skipped for another eligible row;
3. a row waiting for backoff does not block another eligible row;
4. two DLQ workers do not concurrently claim the same dead-letter row;
5. unique `original_event_id` prevents duplicate durable dead-letter creation.

PostgreSQL row locking with `SKIP LOCKED` remains the concurrency primitive.

## Failure matrix

### Primary success

- primary row -> `PUBLISHED`;
- `published_at` populated;
- active primary error fields cleared;
- no dead-letter row.

### Retriable primary failure, attempts 1-4

- primary row remains `PENDING`;
- `attempt_count` increments;
- `next_attempt_at` scheduled;
- sanitized error metadata persisted;
- no dead-letter row.

### Retriable primary failure, attempt 5

Atomically:

- primary row -> `DEAD_LETTERED`;
- `attempt_count = 5`;
- final primary error metadata persisted;
- exactly one dead-letter row -> `PENDING`.

### Non-retriable primary failure

Atomically:

- primary row -> `DEAD_LETTERED` immediately;
- exactly one dead-letter row -> `PENDING`;
- no unnecessary primary retries.

### DLQ Kafka failure

- dead-letter row stays `PENDING`;
- `publish_attempts` increments;
- `next_attempt_at` follows 5s, 15s, 30s, then capped 60s;
- DLQ publication error fields updated;
- no secondary dead-letter row.

### Database failure while recording retry/dead-letter state

- transaction rolls back;
- prior durable state remains authoritative;
- no false `PUBLISHED` or `DEAD_LETTERED` status is committed.

## Testing strategy

### Unit tests

Cover:

- primary backoff selection;
- fifth-attempt dead-letter decision;
- failure classification;
- sanitization/truncation;
- primary state transitions;
- clearing primary error fields after eventual success;
- DLQ backoff with 60s cap;
- DLQ state transitions;
- clearing DLQ publication error fields after eventual success;
- batch continuation after handled failures.

### PostgreSQL integration tests

Cover:

- Flyway migration from v0.6-compatible data;
- defaults, constraints, indexes;
- due-event selection via `next_attempt_at`;
- `SKIP LOCKED` concurrency;
- atomic primary dead-letter transition;
- unique `original_event_id`;
- durable retry state across transactions.

### Kafka integration tests

Cover:

- transient primary failure schedules retry;
- later success publishes the same event contract and marks `PUBLISHED`;
- fifth failure creates a dead-letter row;
- non-retriable failure dead-letters immediately;
- dead-letter publication reaches `corebank.financial-events.dlq.v1`;
- DLQ failure persists backoff state;
- later DLQ recovery marks `PUBLISHED`;
- primary and DLQ payloads exclude sensitive/free-form data.

## Regression gate

Final release verification:

```text
mvn clean verify
```

v0.7 is not GREEN until fresh output proves `BUILD SUCCESS` with zero reported failures/errors.

## Release workflow

Branch:

```text
feature/corebank-v0.7
```

Workflow:

1. implement only on feature branch;
2. final local `mvn clean verify`;
3. review full diff against this spec;
4. open PR to `main`;
5. never merge without explicit user approval;
6. squash merge after approval;
7. verify `main`;
8. create annotated tag `v0.7.0` only after merge verification.

## Acceptance criteria

v0.7 is complete only when:

1. primary retry state survives restarts;
2. primary retry timing is 2s, 5s, 15s, 30s;
3. attempt five dead-letters retriable failures;
4. non-retriable failures dead-letter immediately;
5. primary dead-letter transition and dead-letter-row creation are atomic;
6. DLQ topic is `corebank.financial-events.dlq.v1`;
7. DLQ retries indefinitely using 5s, 15s, 30s, then capped 60s;
8. no DLQ-of-DLQ exists;
9. no redrive exists in v0.7;
10. error persistence is bounded and sanitized;
11. successful eventual publication retains attempt counters but clears active error fields;
12. `SKIP LOCKED` concurrency works for both publishers;
13. financial operations remain independent of Kafka availability;
14. fresh `mvn clean verify` evidence is GREEN before merge.
