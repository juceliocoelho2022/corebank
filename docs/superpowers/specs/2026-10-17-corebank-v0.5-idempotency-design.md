# CoreBank v0.5 — Idempotency Design

Date: 2026-10-17

## Status

Approved architectural design for CoreBank v0.5. Implementation must not begin until the written implementation plan is reviewed and execution method selected.

## Goal

Add persistent HTTP idempotency to CoreBank financial commands so client retries cannot duplicate financial effects.

Version v0.5 covers only:

- deposits;
- withdrawals;
- internal account-to-account transfers.

Customer and account creation remain outside the v0.5 idempotency scope.

## Current architecture constraints

CoreBank v0.4 is a modular monolith using Java 21, Spring Boot 3.5.6, PostgreSQL, Flyway, Spring Data JPA, Testcontainers, JaCoCo and Docker Compose.

The financial write paths already persist operational balance, immutable transaction history and double-entry ledger entries atomically inside Spring transactions. Idempotency must compose with those guarantees, not bypass them.

No frontend work is part of v0.5.

## HTTP contract

The following endpoints require an `Idempotency-Key` header:

- `POST /api/v1/accounts/{accountId}/deposits`
- `POST /api/v1/accounts/{accountId}/withdrawals`
- `POST /api/v1/transfers`

### Header rules

`Idempotency-Key` is mandatory for all three financial POST endpoints.

Rules:

- minimum length: 8 characters;
- maximum length: 128 characters;
- treated as an opaque value;
- no case folding or semantic normalization;
- globally unique within CoreBank v0.5.

Missing or invalid keys return `400 Bad Request`.

## Core semantics

A key is bound to both an operation type and a canonical request fingerprint.

### First request

For a new key:

1. reserve the key;
2. persist an `IN_PROGRESS` idempotency record;
3. execute the financial command;
4. persist operational balance/history/ledger effects;
5. persist the original HTTP response data;
6. mark the idempotency record `COMPLETED`;
7. commit all changes atomically.

The first response includes:

`Idempotent-Replayed: false`

### Exact retry

For the same key, same operation type and same request hash after the first request is `COMPLETED`:

- do not execute the financial command again;
- do not change balances;
- do not create another `account_transactions` row;
- do not create another journal;
- do not create another ledger entry;
- return the persisted original HTTP response;
- return the original HTTP status.

The replay response includes:

`Idempotent-Replayed: true`

### Key reuse with different request

If the same key is reused with a different operation type or request fingerprint, return `409 Conflict`.

No new financial side effect is allowed.

### Key currently in progress

If another request encounters the same key in `IN_PROGRESS`, return `409 Conflict` with a sanitized problem response indicating that an operation for the key is already in progress.

The server does not block the request thread and does not internally poll for completion.

A later retry after the first transaction commits may replay the `COMPLETED` response.

## Persistence model

Introduce a Flyway migration:

`V5__create_idempotency_records.sql`

Table:

```text
idempotency_records
├── id UUID PRIMARY KEY
├── idempotency_key VARCHAR(128) NOT NULL UNIQUE
├── operation_type VARCHAR(32) NOT NULL
├── request_hash CHAR(64) NOT NULL
├── status VARCHAR(16) NOT NULL
├── resource_id UUID NULL
├── response_body JSONB NULL
├── http_status INTEGER NULL
├── created_at TIMESTAMPTZ NOT NULL
└── completed_at TIMESTAMPTZ NULL
```

### Supported operation types

```text
DEPOSIT
WITHDRAWAL
TRANSFER
```

### Supported statuses

```text
IN_PROGRESS
COMPLETED
```

### Database invariants

The migration must enforce:

- globally unique `idempotency_key`;
- allowed `operation_type` values only;
- allowed `status` values only;
- `request_hash` stored as a SHA-256 hex digest of exactly 64 characters;
- `COMPLETED` records must have non-null `response_body`, `http_status` and `completed_at`;
- `IN_PROGRESS` records may leave completion metadata null.

## Transaction boundaries

The idempotency record must participate in the same database transaction as the financial operation.

Conceptually:

```text
BEGIN
  reserve idempotency key as IN_PROGRESS
  execute financial command
  update operational balance
  persist account history
  persist double-entry journal and ledger entries
  persist response replay data
  mark idempotency record COMPLETED
COMMIT
```

Any exception rolls the whole transaction back.

Therefore:

- a failed financial operation must not leave a stale `IN_PROGRESS` record;
- a failed ledger/history/balance write must also roll back the idempotency reservation;
- no successful financial effect may exist without its completed idempotency record for an idempotent request.

## Concurrency strategy

PostgreSQL is the authority for duplicate-key exclusion.

Primary guarantee:

```text
UNIQUE(idempotency_key)
```

No JVM-local lock or in-memory map is permitted as the correctness mechanism because the design must remain valid with multiple application instances.

Concurrent requests using the same key must result in at most one financial execution.

## Request fingerprinting

Use SHA-256 over a deterministic canonical request representation, not the raw JSON body.

This prevents harmless JSON formatting differences from producing different hashes.

### Deposit canonical fields

```text
operation=DEPOSIT
accountId
amount
description
```

### Withdrawal canonical fields

```text
operation=WITHDRAWAL
accountId
amount
description
```

### Transfer canonical fields

```text
operation=TRANSFER
sourceAccountId
destinationAccountId
amount
description
```

Rules:

- monetary amount must be rendered deterministically at monetary scale, e.g. `100.00`;
- descriptions use the existing normalized business representation;
- null description is represented deterministically;
- field order is fixed by implementation;
- UUIDs use their canonical string form.

The SHA-256 digest is stored as lower-case hexadecimal.

## Response replay

When the original request completes, persist:

- `resource_id` where meaningful;
- response body as `JSONB`;
- original HTTP status;
- completion timestamp.

Replay returns the same response body and same HTTP status.

Examples:

- original deposit: `201 Created`;
- replayed deposit: `201 Created`;
- original transfer: `201 Created`;
- replayed transfer: `201 Created`.

Only the `Idempotent-Replayed` header distinguishes initial execution from replay.

## Application architecture

Introduce a dedicated module:

```text
com.corebank.idempotency
├── domain
├── application
├── infrastructure
└── web
```

The idempotency layer owns:

- key validation;
- operation classification;
- request fingerprinting;
- reservation;
- replay lookup;
- conflict detection;
- in-progress detection;
- response persistence.

Existing financial application services continue to own financial business logic.

Desired flow:

```text
Controller
   ↓
Idempotency application layer
   ↓
TransactionService / TransferService
   ↓
Account + account_transactions + Ledger
```

The v0.5 design must avoid duplicating idempotency rules separately inside `TransactionService` and `TransferService`.

## Error semantics

### 400 Bad Request

Used for:

- missing `Idempotency-Key`;
- key shorter than 8 characters;
- key longer than 128 characters;
- otherwise structurally invalid key input.

### 409 Conflict

Used for:

- key reused with a different operation type;
- key reused with a different request hash;
- key already reserved and currently `IN_PROGRESS`.

### Existing business errors

Existing financial errors remain unchanged, including insufficient funds, inactive accounts and concurrency conflicts.

A failed business operation must not be stored as `COMPLETED` in v0.5.

## Retention

Version v0.5 has no TTL and no scheduled cleanup.

Idempotency records persist indefinitely.

Reasons:

- avoids re-executing an old financial operation after record expiration;
- keeps v0.5 deterministic;
- avoids introducing retention policy before operational requirements exist.

Redis is explicitly out of scope for v0.5 and remains planned for v0.8.

## Key namespace

Keys are global in v0.5:

```text
UNIQUE(idempotency_key)
```

Authentication/client scoping is not yet available.

When JWT/RBAC arrives later, the model may evolve toward a scoped uniqueness rule such as `(client_id, idempotency_key)`.

## Test strategy

All implementation follows TDD.

Minimum required scenarios:

1. first request executes normally;
2. exact retry with same key and payload does not duplicate effects;
3. exact retry returns the same persisted response;
4. replay returns `Idempotent-Replayed: true`;
5. first execution returns `Idempotent-Replayed: false`;
6. same key with different payload returns `409`;
7. same key with different operation returns `409`;
8. missing key returns `400`;
9. invalid key returns `400`;
10. concurrent same-key requests produce at most one financial execution;
11. business failure leaves no `COMPLETED` record;
12. rollback of ledger/history/balance also removes the idempotency reservation;
13. deposit is idempotent;
14. withdrawal is idempotent;
15. transfer is idempotent.

Testing layers:

- domain/unit tests;
- service tests;
- MVC/controller tests;
- persistence integration tests;
- concurrency integration tests;
- full regression with `mvn clean verify`;
- whitespace check with `git diff --check main...HEAD`.

## Primary acceptance scenarios

### Deposit replay

Request repeated twice:

```text
POST /api/v1/accounts/{accountId}/deposits
Idempotency-Key: payment-123
amount = 100.00
```

Required committed state:

```text
account balance       = 100.00
account_transactions  = 1 row
journal_entries       = 1 row
ledger_entries        = 2 rows
idempotency_records   = 1 row
```

Second request returns the original response without creating any additional financial rows.

### Transfer replay

For a repeated transfer with the same key and same payload:

```text
source debit          = exactly once
destination credit    = exactly once
TRANSFER_OUT history  = 1 row
TRANSFER_IN history   = 1 row
journal_entries       = 1 row
ledger_entries        = 2 rows
idempotency_records   = 1 row
```

## Release target

Version after completion:

`0.5.0`

Release capabilities:

- persistent HTTP idempotency;
- safe financial retries;
- payload conflict detection;
- concurrent duplicate protection;
- response replay;
- PostgreSQL-backed correctness guarantees.

## Out of scope

The following are intentionally excluded from v0.5:

- frontend;
- Redis-based idempotency;
- TTL/cleanup jobs;
- idempotency for customer creation;
- idempotency for account creation;
- authentication/client-scoped keys;
- Kafka/event publication;
- retry/DLQ infrastructure;
- observability metrics implementation.
