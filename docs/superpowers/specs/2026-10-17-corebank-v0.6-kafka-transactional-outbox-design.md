# CoreBank v0.6 — Kafka Events with Transactional Outbox

Date: 2026-10-17
Status: Design approved
Target release: 0.6.0
Base release: 0.5.0

## 1. Purpose

CoreBank v0.6 introduces asynchronous financial-event publication through Apache Kafka without weakening the transactional guarantees established in previous releases.

The primary architectural problem is dual-write consistency: a financial transaction must never be considered successful while its corresponding integration event is silently lost because Kafka was unavailable at commit time.

The chosen solution is a PostgreSQL-backed Transactional Outbox. Financial state and the durable integration event are committed atomically in the same database transaction. A separate publisher later delivers pending outbox rows to Kafka.

The release remains a modular monolith. Kafka is introduced as an integration boundary, not as a reason to split the application into microservices.

## 2. Goals

v0.6 must demonstrate:

- durable domain-event creation for successful deposits, withdrawals and internal transfers;
- no direct database + Kafka dual write inside the financial request transaction;
- PostgreSQL Transactional Outbox;
- Kafka publication after financial commit;
- at-least-once delivery semantics;
- non-blocking financial APIs when Kafka is unavailable;
- no duplicate outbox event caused by HTTP idempotency replay;
- safe concurrent outbox processing by multiple CoreBank instances;
- explicit event envelopes and versioned event contracts;
- minimal exposure of customer-sensitive data;
- integration testing with PostgreSQL and Kafka through Testcontainers.

## 3. Non-goals

The following are intentionally outside v0.6:

- DLQ;
- exponential backoff;
- configurable maximum retry attempts;
- poison-message policy;
- Redis;
- business consumers;
- Kafka exactly-once semantics;
- Kafka transactions coupled to JPA transactions;
- Schema Registry;
- Avro or Protobuf;
- JWT/RBAC;
- custom Prometheus metrics;
- service extraction or microservices.

Retry policy and DLQ belong to v0.7.

## 4. Architectural decision

### 4.1 Rejected: direct Kafka publication from the financial transaction

Publishing directly through `KafkaTemplate` from deposit, withdrawal or transfer flows creates a dual-write problem because PostgreSQL and Kafka are separate transactional resources.

Possible failure modes include:

- PostgreSQL commits while Kafka publication fails;
- Kafka receives an event while the financial database transaction later rolls back;
- ambiguous timeout responses leave the application unable to know which side committed.

This approach is rejected for v0.6.

### 4.2 Rejected: coordinated Kafka/JPA transactions

Spring/Kafka transaction coordination would introduce significantly more operational and conceptual complexity while still coupling the HTTP financial path to broker availability.

This is unnecessary for the current project goals.

### 4.3 Selected: Transactional Outbox

The selected flow is:

```text
HTTP request
   ↓
IdempotencyService
   ↓
TransactionService / TransferService
   ↓
PostgreSQL transaction
   ├── accounts
   ├── account_transactions
   ├── journal_entries
   ├── ledger_entries
   ├── idempotency_records
   └── outbox_events
            ↓
          COMMIT
            ↓
      OutboxPublisher
            ↓
          Kafka
```

The core invariant is:

```text
financial commit => durable outbox event
```

Kafka availability is not part of financial transaction success.

## 5. Financial events

v0.6 defines exactly three integration-event types:

```text
DEPOSIT_COMPLETED
WITHDRAWAL_COMPLETED
TRANSFER_COMPLETED
```

Each successful business operation produces exactly one corresponding outbox event.

A transfer produces one `TRANSFER_COMPLETED` event, not one event per `TRANSFER_OUT` / `TRANSFER_IN` history row.

## 6. Event envelope

All Kafka messages use a stable event envelope:

```json
{
  "eventId": "uuid",
  "eventType": "TRANSFER_COMPLETED",
  "eventVersion": 1,
  "occurredAt": "2026-10-17T15:40:00Z",
  "aggregateType": "TRANSFER",
  "aggregateId": "uuid",
  "correlationId": "uuid",
  "payload": {}
}
```

### 6.1 Envelope semantics

- `eventId`: unique UUID for this event instance; used by consumers for deduplication.
- `eventType`: stable business-event name.
- `eventVersion`: starts at `1` and changes when the event contract evolves incompatibly.
- `occurredAt`: UTC timestamp representing when the business event was created.
- `aggregateType`: business aggregate represented by the event.
- `aggregateId`: principal business aggregate identifier.
- `correlationId`: identifier of the originating financial operation.
- `payload`: event-specific business data.

The persisted `outbox_events.id` is the same UUID exposed as `eventId` in the Kafka envelope. CoreBank must not generate a second identifier for the same event.

Persistence entities must never be serialized directly as event contracts.

## 7. Event payloads

### 7.1 DEPOSIT_COMPLETED

```json
{
  "eventId": "uuid",
  "eventType": "DEPOSIT_COMPLETED",
  "eventVersion": 1,
  "occurredAt": "2026-10-17T15:40:00Z",
  "aggregateType": "ACCOUNT",
  "aggregateId": "account-uuid",
  "correlationId": "transaction-uuid",
  "payload": {
    "accountId": "account-uuid",
    "transactionId": "transaction-uuid",
    "amount": 100.00,
    "currency": "BRL"
  }
}
```

For deposits:

```text
aggregateId   = accountId
correlationId = AccountTransaction.id
message_key   = accountId
```

### 7.2 WITHDRAWAL_COMPLETED

```json
{
  "eventId": "uuid",
  "eventType": "WITHDRAWAL_COMPLETED",
  "eventVersion": 1,
  "occurredAt": "2026-10-17T15:41:00Z",
  "aggregateType": "ACCOUNT",
  "aggregateId": "account-uuid",
  "correlationId": "transaction-uuid",
  "payload": {
    "accountId": "account-uuid",
    "transactionId": "transaction-uuid",
    "amount": 50.00,
    "currency": "BRL"
  }
}
```

For withdrawals:

```text
aggregateId   = accountId
correlationId = AccountTransaction.id
message_key   = accountId
```

### 7.3 TRANSFER_COMPLETED

```json
{
  "eventId": "uuid",
  "eventType": "TRANSFER_COMPLETED",
  "eventVersion": 1,
  "occurredAt": "2026-10-17T15:42:00Z",
  "aggregateType": "TRANSFER",
  "aggregateId": "transfer-uuid",
  "correlationId": "transfer-uuid",
  "payload": {
    "transferId": "transfer-uuid",
    "sourceAccountId": "source-uuid",
    "destinationAccountId": "destination-uuid",
    "amount": 125.00,
    "currency": "BRL"
  }
}
```

For transfers:

```text
aggregateId   = transferId
correlationId = transferId
message_key   = sourceAccountId
```

The source-account Kafka key is intentionally distinct from `aggregateId`. This supports ordered publication for events originating from the same source account while keeping the business aggregate itself as `TRANSFER`.

## 8. Sensitive-data policy

The event contract must not include:

- customer name;
- customer e-mail;
- CPF or other government identifier;
- passwords, PINs or authentication data;
- complete account balance;
- original HTTP request body;
- `Idempotency-Key`;
- stack traces;
- infrastructure-internal diagnostic objects.

Free-form financial `description` is also excluded in v0.6 because it may contain user-entered sensitive data.

## 9. Outbox persistence model

Migration v0.6 will create:

```text
outbox_events
├── id UUID PK
├── event_type VARCHAR(64) NOT NULL
├── event_version INTEGER NOT NULL
├── aggregate_type VARCHAR(64) NOT NULL
├── aggregate_id UUID NOT NULL
├── correlation_id UUID NOT NULL
├── message_key VARCHAR(128) NOT NULL
├── payload JSONB NOT NULL
├── status VARCHAR(16) NOT NULL
├── created_at TIMESTAMPTZ NOT NULL
└── published_at TIMESTAMPTZ NULL
```

### 9.1 Status values

```text
PENDING
PUBLISHED
```

No `FAILED` status is introduced in v0.6.

### 9.2 Database invariants

The migration must enforce at least:

```text
event_version >= 1
status IN ('PENDING', 'PUBLISHED')
PENDING   => published_at IS NULL
PUBLISHED => published_at IS NOT NULL
```

`event_type`, `aggregate_type`, `message_key` and payload must be non-null.

### 9.3 Index

Pending-event polling must be supported by a partial index:

```sql
CREATE INDEX idx_outbox_pending_created_at
ON outbox_events (created_at)
WHERE status = 'PENDING';
```

Ordering is oldest-first.

## 10. Financial transaction boundary

The outbox event is recorded inside the same Spring/PostgreSQL transaction as the financial state and the idempotency record.

Conceptual deposit flow:

```text
BEGIN
  acquire idempotency lock
  reserve idempotency record IN_PROGRESS
  update account balance
  insert account_transaction
  insert journal_entry
  insert ledger_entries
  insert outbox_event PENDING
  persist original idempotent response
  mark idempotency record COMPLETED
COMMIT
```

If any step fails, the whole transaction rolls back.

Therefore the following states are forbidden:

```text
financial state committed + missing durable outbox event
outbox event committed + financial transaction rolled back
```

## 11. Interaction with v0.5 idempotency

HTTP replay must not create another event.

The rule is:

```text
1 real financial operation = 1 outbox event
```

not:

```text
1 HTTP attempt = 1 outbox event
```

For a completed idempotency record, the replay path returns the persisted response and bypasses the financial command; it therefore must also bypass outbox creation.

Acceptance evidence must assert that repeated requests with the same valid `Idempotency-Key` leave the outbox count unchanged.

## 12. Application structure

The new subsystem is named `event`:

```text
com.corebank.event
├── domain
│   ├── DomainEventType
│   ├── OutboxStatus
│   └── OutboxEvent
├── application
│   ├── FinancialEventFactory
│   └── OutboxService
└── infrastructure
    ├── OutboxEventRepository
    ├── OutboxPublisher
    └── OutboxScheduler
```

The controllers do not create integration events.

Financial application services call `OutboxService` only after the corresponding financial effects and ledger posting have succeeded, while remaining inside the same outer transaction.

The event factory owns envelope and payload construction so Kafka contracts do not leak JPA entities.

## 13. Kafka topology

v0.6 uses one topic:

```text
corebank.financial-events.v1
```

Local-development defaults:

```text
partitions = 3
replication-factor = 1
```

The topic may be declared through Spring Kafka `NewTopic` configuration.

No business consumer is part of v0.6.

## 14. Kafka message key

The outbox stores the exact Kafka message key in `message_key`.

Rules:

```text
DEPOSIT_COMPLETED    -> accountId
WITHDRAWAL_COMPLETED -> accountId
TRANSFER_COMPLETED   -> sourceAccountId
```

The publisher must not deserialize `payload` in order to determine the Kafka key.

## 15. Publication model

The publisher processes durable `PENDING` rows after the financial transaction has committed.

Conceptual flow:

```text
outbox_events PENDING
       ↓
claim row
       ↓
KafkaTemplate.send(topic, message_key, json)
       ↓
Kafka ACK
       ↓
mark PUBLISHED + published_at
```

A row must never be marked `PUBLISHED` before Kafka acknowledges the send.

## 16. Multi-instance concurrency

Multiple CoreBank instances may run the publisher concurrently.

Pending events must be claimed using PostgreSQL locking equivalent to:

```sql
SELECT *
FROM outbox_events
WHERE status = 'PENDING'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT :batchSize;
```

This avoids JVM-local coordination and allows other instances to skip already-claimed rows.

The database remains the correctness authority.

## 17. Delivery semantics

v0.6 guarantees at-least-once publication, not exactly-once delivery.

Critical crash window:

```text
Kafka ACK received
↓
process crashes before PUBLISHED is committed
↓
row remains PENDING
↓
row may be sent again
```

This duplication is accepted and documented.

Every event has a unique `eventId` so future consumers can implement inbox/deduplication logic.

No claim of end-to-end exactly-once semantics is permitted.

## 18. Scheduler and retry

The outbox scheduler runs periodically and asks the publisher to process pending events.

Initial configuration:

```yaml
corebank:
  outbox:
    batch-size: 100
    fixed-delay-ms: 2000
```

Both values must be externally configurable.

Retry behavior in v0.6 is intentionally simple:

```text
publication failure => event remains PENDING
next scheduler cycle => try again
```

There is no exponential backoff, maximum attempt count or DLQ until v0.7.

## 19. Per-event completion behavior

A publication failure for one event must not require already-confirmed prior events to remain pending merely because they were processed in the same selected batch.

Conceptually:

```text
event A -> Kafka ACK -> PUBLISHED
event B -> Kafka ACK -> PUBLISHED
event C -> failure  -> remains PENDING
```

The implementation plan must choose transaction boundaries that preserve this observable behavior without holding unnecessary PostgreSQL locks for long broker calls.

## 20. Kafka unavailability

Kafka unavailability must not cause a valid financial HTTP request to fail.

Example:

```text
Kafka unavailable
↓
deposit request
↓
financial transaction commits
outbox row commits as PENDING
HTTP returns the normal successful financial response
```

When Kafka recovers, a later scheduler cycle publishes the pending event.

## 21. Serialization

The publisher uses:

```text
KafkaTemplate<String, String>
```

The event envelope is serialized explicitly with Jackson/ObjectMapper to JSON.

This prevents Java entity/class metadata from becoming part of the external integration contract.

## 25. Logging

v0.6 adds only the minimum structured context needed to diagnose publication:

```text
eventId
eventType
aggregateId
status
topic
```

An attempt counter is not persisted in v0.6 because attempt/backoff policy belongs to v0.7.

Do not log sensitive payload data by default.

## 26. Testing strategy

### 26.1 Migration and persistence

Tests must prove:

- `outbox_events` schema exists;
- JSONB payload persists correctly;
- status constraints are enforced;
- `published_at` consistency is enforced;
- pending-event index exists where practical to assert;
- state transition `PENDING -> PUBLISHED` works.

### 26.2 Financial-operation integration

For a successful deposit, assert:

```text
balance change = 1
account_transaction = 1
journal = 1
ledger entries = 2
outbox events = 1
```

For a successful withdrawal, assert one `WITHDRAWAL_COMPLETED` outbox event.

For a successful transfer, assert one and only one `TRANSFER_COMPLETED` event.

### 26.3 Idempotency integration

For first execution:

```text
financial effects = 1
outbox events = 1
```

For exact replay:

```text
financial effects remain = 1
outbox events remain = 1
```

### 26.4 Rollback integration

Force a failure late enough in the transactional path to prove:

```text
balance unchanged
history unchanged
ledger unchanged
idempotency record absent
outbox event absent
```

### 26.5 Kafka publication integration

Use Testcontainers PostgreSQL + Kafka to prove:

```text
financial operation
↓
outbox PENDING
↓
publisher runs
↓
Kafka test consumer receives expected key + JSON envelope
↓
outbox becomes PUBLISHED
```

### 26.6 Kafka failure behavior

Tests must prove that failed publication leaves the event `PENDING` and does not modify the already-committed financial result.

### 26.7 Concurrent publisher behavior

Tests must provide evidence that concurrent publisher workers do not intentionally process the same pending row simultaneously and that `SKIP LOCKED` allows progress on other rows.

## 27. Release acceptance criteria

CoreBank v0.6 is ready only when all of the following are supported by fresh test evidence:

```text
successful financial operation
    => exactly one durable outbox row

idempotent HTTP replay
    => zero additional outbox rows

financial rollback
    => zero committed outbox rows

Kafka unavailable
    => financial request can still succeed
    => outbox remains PENDING

Kafka ACK
    => event becomes PUBLISHED

two publisher workers/instances
    => locked rows are skipped safely

crash after Kafka ACK but before PUBLISHED commit
    => duplicate publication is possible and documented
    => at-least-once semantics remain explicit
```

Final regression gate:

```text
mvn clean verify
```

No release claim may be made without a fresh successful full build.

## 29. Success criteria

The release succeeds if it demonstrates that CoreBank can publish integration events reliably without coupling banking transaction availability to Kafka availability.

The defining properties are:

```text
PostgreSQL transaction = financial source of truth
Transactional Outbox   = durable integration handoff
Kafka                   = asynchronous delivery channel
at-least-once           = explicit delivery guarantee
```

The system must favor correctness and explainability over premature distributed-system complexity.
